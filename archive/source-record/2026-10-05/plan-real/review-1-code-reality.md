# Review 1: code and dependency reality (CRITIC 1)

Target: `plan-real/v2-synthesis.md`. Evidence base: read-only worktree `improvement-engine-main-ro` (main 41492cb), `estado-spec/01`, `Cargo.lock`, `~/.cargo/registry/cache`, `git log`/`gh api` PR metadata (#71-#93), shared journal, llm-gateway via `gh api`, host probes (nvidia-smi, podman machine list). Nothing was compiled or run.

## 1. Verdict

1. The plan's macro-shape (thin thread, seam crates, durable executor behind a `JobHandler` ABI) is right, but several "exists / just wire it" premises are false at the signature level: the Rust ports are digest-only, the compiler accepts exactly one `Add Flow` shape, the writer is a Core stage (not HTTP routes), and no PG job adapter, migration runner or claim-next query exists (F-1, F-2, F-3).
2. The tripwire fallback F-PY is not credible for compile and gate steps: capability types are deliberately non-deserializable (171 of 459 pub types derive serde; 54 `compile_fail` guards), so a JSON-in/JSON-out `pulso-engine step` cannot cover them (F-4).
3. Hours are mis-distributed rather than uniformly wrong: Python-side WPs look 2-3x too high against measured Claude throughput, Rust-seam and PG WPs look 1.3-1.8x too low, and about 70% of the T0-T1a hours are Rust that is gated by a cargo slot with 25-35 min gates (F-5, F-6). T1a by S7 is about 30-35%, not 55%.
4. DEBATE-1: sync (confirmed, with a stronger reason than the plan gives). DEBATE-2: Claude owns adapter plus worker end to end; Codex owns an offline conformance suite and review (section 3).
5. S-MAP can only get a first read in session 1, not a verdict; the harness path that works in session 1 is Python plus the existing e2e double plus the real gateway (F-8).

## 2. Findings

- Why it matters: the scout, verifier and builder return `pulso_hypotheses` / `pulso_verification` / `pulso_change_spec` facts (`stages/catalog.py`), and the engine must read them. A client that "implements `CoreTaskPort`" cannot return them. Bumping the constants to c814c2b changes every Codex test keyed on 0.5.0. This is a Codex-owned contract change needed on day 1 of T0, while Codex is frozen.
- Edit: K2 must define its own typed client API (`invoke -> InvokeResult{ receipt, facts }`, arms, admissions, dry-run, alias read) in `crates/core-client`, with the `CoreTaskPort` bridged by a thin adapter later; or record U-2 explicitly as allowing Claude to make the `core_task.rs` constant/shape change as an approved exception with a `[CONTRACT-CHANGE]` stanza. Remove the sentence in 5.3 that existing ports are the contract; the contract is `bridge-contract/` only. Add 4-6 h for the port rework to K2 and list `core_task.rs` as a shared touch point in OWNERS.

### F-2 (BLOCKER for K3/D-MAP sizing) The compiler and the writer path are narrower and different from what K3 assumes
- Plan: K3 "ChangeSpec subset to EntityDraft[] (Add ToolDef, Replace Flow, Replace Agent), writer create/PUT/validate/freeze with readback"; D-MAP "`change_compiler.rs` extension to Flow add/replace, Prompt, DecisionModel", 12-20 h; K3 deps = K1 + S-MAP only; K3 12-16 h.

- Edit: re-spec K3 as "draft-plan artifact + commitment sealing + writer invoke + receipt/readback check + dry-run"; set the first compile subset to `Replace Prompt` + `Add EvalSuite` (matches e2e `candidate_changes` and stage prompts in `agent-core-assets/worlds/pulso-evolution/prompts`), with Flow-add as the second kind; make D-MAP-compile an explicit predecessor of K3-writer (add edge `D-MAP(compile) -> K3`); sizing K3 18-26 h, D-MAP 16-26 h. ### F-4 (HIGH) `pulso-engine step` pure-step CLI and the F-PY fallback do not cover compile/gate
- Plan: E3 "every semantic step is a pure JSON in, JSON out function first" 4-6 h; fallback F-PY "Python shell over `pulso-engine step` for sensors, compile and gate" (4.3 tripwire; C section 3.1; R4 mitigation).
- Evidence: serde derives exist on only 171 of 459 pub types, concentrated in sensors, e0_* packets, scout/verifier, memory publication, platform_* and `local_simulation` (grep). - Edit: (1) rescope E3 to "evidence-side steps" (D-WIRE outputs) 6-8 h; (2) rewrite F-PY honestly: Python shell may drive sensors and verifier via `step`, but compile/gate are labelled `stand-in` (Python draft builder as in `codex_standin`) in that fallback; (3) move the tripwire to end of session 3 for the specific check "a Rust `core-client` has invoked scout/verifier against the real image" and keep end-of-S4 only for steps 4-5; (4) add a WP `WIRE-DTO` (Codex, 10-15 h) defining serializable state snapshots between steps if the executor is to be restart-safe at all (needed by E6 regardless, because a worker restart must resume a job from stored `input_ref/config_ref`, not from in-memory capabilities; see F-7).

### F-7 (HIGH) The run-once/in-memory-then-PG ABI hides a state-serialization problem
- Plan: E1 "handler(job, ports) to outcome ... in-memory store with file snapshot"; T1b "same thread, but jobs on PG".
- Evidence: capability objects (F-4) cannot be persisted; jobs on `pulso_jobs` carry only `input_ref`, `config_ref` (artifact refs) and `run_ref`. A killed worker resumes a job from stored refs, so each handler's inputs must be re-derivable from artifacts in the PG artifact store (migration 0001 CAS), and the capabilities re-minted by a trusted constructor path. Today the opaque types are minted in-process by the previous step.
- Edit: add to E1's first RED a "kill between handler N and N+1 then resume from store only" test already in T1a (not T1b), and make the run-once harness persist inputs through the CAS `ArtifactRepository` (exists, 8 tests plus PG test) instead of "file snapshot". Cost +6-10 h in T1a, saves a rewrite at T1b.

## 3. Resolution of assigned DEBATE items

### DEBATE-1: sync `ureq` + `tiny_http` vs axum/tokio

Resolution: sync, in `core-client` and `control-api`, and the case is stronger than the plan states.

Decisive evidence:
1. Every Codex persistence adapter is `&mut self` over the blocking `postgres::Client` 0.19: `lib.rs:9` (`ArtifactRepository`), `model_provider.rs:10`, `platform_observations.rs:7` (`Client`, `Transaction`), `durable_run_events.rs:6`, `run_timeline_v2.rs:12`. That crate runs its own internal tokio runtime and `block_on`s; calling it from an async task panics ("cannot start a runtime from within a runtime"). Under axum every handler would be `spawn_blocking` around these libraries, so async buys no concurrency and adds a second runtime and 40-60 packages. (`tokio` 1.53.1 is already in the lock only as postgres's engine, so the "async tax" is not zero today but is invisible; do not enable its `rt-multi-thread`/`net` features in our crates.)
2. No real model transport is needed (F-10), so the only HTTP client is Core-bridge calls on loopback or Cloud Map; `ureq` with `default-features = false` is enough.
3. Lease/concurrency numbers are small: lab long-poll up to 120 s per query and a handful of SSE viewers; thread-per-request with a bounded pool (N = 16) and a bounded `Mutex<Vec<postgres::Client>>` pool is adequate for T0-T2. There is no 10k-connection requirement in the spec's DoD.
4. Build cost and Windows cargo contention (F-5): fewer packages is a first-order concern here.

Conditions and switch trigger (state before E4): switch to axum only inside `crates/control-api`, with `spawn_blocking` at the domain-trait boundary, if the E9 spike shows any of: SSE clients above 50 concurrent, `tiny_http` cannot detect client disconnects within 5 s, or request-body slow-read stalls a pool thread past the 30 s timeout. Keep the domain traits (`core-client`, broker handlers) free of HTTP types so the swap is mechanical. Accept `tiny_http` low maintenance as a known risk; the swap cost is about 6-10 h. Note HTTP/1.1 only; ALB in TA is fine.

### DEBATE-2: who owns the PG job-store adapter and worker loop

Resolution: Claude owns `PgJobRepository`, the claim-next query, the migrations for it, the worker loop and the PG tests as ONE lane. Codex owns (a) the reducer semantics already in `durable_jobs.rs` as the executable spec, (b) an offline, backend-generic conformance suite over `DurableJobRepository` (the 18 existing in-memory tests rewritten as `fn conformance<R: DurableJobRepository>(make: impl Fn() -> R)` so the same tests run unchanged on PG), and (c) adversarial review of the SQL. Claude's fallback in 9.3 ("end of S5") is replaced by default ownership.

Decisive evidence:
- The trait has no claim-next, no state tables, a status CHECK that cannot hold the plan's outcomes, and DB roles/RLS that must be provisioned (F-3). The first-run failures of SQL with deferred FKs, UUIDv7 CHECKs, SECURITY DEFINER triggers and RLS can only be found against a live PG; Codex's own record shows they needed a disposable DB (journal line 268, "first-RED against `pulso_test` on the Codex-owned VM"), and CX-0172 later records Podman/PG-backed checks "unavailable". Blind SQL by a frozen team without PG puts 35-50 h of T1b serial depth behind a feedback loop that takes one handoff per iteration.
- Split of the pure part stays valuable: a generic conformance suite is the one piece of D-PG that is both offline-testable and reduces risk, and it is cheap (about 6-10 h).
- Conditional switch: if the G0b spike proves Codex can reach a loopback PG (the existing `pulso-codex` machine, or a native Windows PG), give Codex the adapter again and keep Claude on the worker loop and chaos tests.

Estimate: conformance suite 6-10 h (Codex), adapter + migration + MIG0 20-30 h (Claude), worker loop + heartbeat + shutdown 10-14 h (Claude), PG chaos subset 8-12 h. Total D-PG+E6+E8-subset 44-66 h against the plan's 14-24 + 10-14 + 10-14 = 34-52.

### 6.2 Roleplay LLM behind the real gateway: feasible, cheap, valuable, with labelling rules
Evidence:
- The gateway is a fan-out to OpenAI-compatible endpoints chosen by alias (`LLM_ENDPOINTS`, `Endpoint{Alias, BaseURL, APIKeyEnv}`); it POSTs chat/completions once, validates against the schema subset, prices from the caller's price, never retries. `timeout_s` is 1..300 (openapi); Core's invoke client timeout is 600 s (`invoke/core_client.py:25`). A backend that answers in 20-200 s through a queue fits inside the existing ceilings with no gateway or bridge change.
- core-bridge needs only `AGENTCORE_LLM_GATEWAY_URL`/`TOKEN` plus an optional stage policy pin (`llm/policy.py`: alias, model, price, max_tokens). A policy entry `endpoint_alias: roleplay`, `model: agent_roleplay@1`, price 0 passes `ModelPolicy.check`. Metering needs `usage_known=true`, so the shim must return token counts (estimated, flagged), else the reservation is kept `unknown` (`metering.py`).
- No Rust code is on this path (F-10). `OpenAiCompatibleTransport` (`model_provider.rs:937`) is a port over endpoint/model/credential_ref; the same shim is a valid real HTTP target for it if Rust ever calls models directly.
Design (about 6-10 h, Claude, Python, in the style of `local/core/doubles`):
1. `roleplay-llm` shim: OpenAI `POST /v1/chat/completions` (+ `/v1/models`). It persists each request (system = Core stage prompt, user = RFC 8785 canonical inputs, schema hints) to a durable queue dir with a request id and long-polls under the gateway `timeout_s` until `responses/<id>.json` appears. A subagent role, given only the request file, writes the response.
2. Main extra work: the scout/verifier use an agent node with tools (`agent_node_tools` in `stages/catalog.py`), so the shim must support multi-turn OpenAI `tool_calls` responses (the subagent chooses the next tool call, Core executes it, the shim receives tool results as the next message). "Acts" therefore means emitting tool-call JSON, not touching the repo. Budget 3-5 h of the 6-10.
3. Labelling: model `agent_roleplay@<role>` is echoed by the gateway; the G1 `doubles[]` generator classifies alias `roleplay` as `agent_roleplay`; honesty tests: such a run cannot be labelled `real` or `local-model`, carries `quality_claims: forbidden`, and the E0 data class stays `E0-local`.
4. Jev: the gateway side exists on main (`POST /v1/jev`, merged PR #2; `JEV_BASE_URL` accepts http on loopback), so a roleplay JEV server exercises the gateway pass-through for real. It does NOT unblock the consumer: agent-core c814c2b has no DecisionProvider that calls `/v1/jev` (PR #28 not on main), so Core runs would not call it. It tests our Rust `JevDecisionPort` adapter and the gateway path in isolation (about 4-6 h); Core-run Jev stays `blocked(jev)`. This corrects section 9.3 item 2: the gateway already has `/v1/jev`; what is missing is the agent-core side.
Benefits: real HTTP path bridge -> gateway -> provider alias with real timeouts, `invalid_output` handling, usage and cost metering and receipts; removes the Ollama install, model pull and VRAM tuning from the session-1 critical path (F-8); S-MAP measures mapping logic with a capable answerer rather than 8B-14B schema compliance; recorded request-digest -> response pairs give deterministic replay (label `recorded`).
Risks and rules:
- It proves plumbing and mapping, not model quality, cost or latency. M3 and M4 stay mandatory before any quality claim.
- Leakage: the roleplay subagent must see only what a real model would see (the request body), never the repo or dataset, or it can recite the "winning complaint". Run it as a separate agent whose only input is the queue file and record its prompt digest.
- Latency and concurrency: a scout run can issue 5-20 model calls, so a run takes minutes and the shim serializes; set `timeout_s` 120-300 and stage timeouts accordingly. Core quotas (R13) and the metering reservation still apply.
- Fault tests (timeout after send, 502 `invalid_output` with usage) need a scripted-fault side channel in the shim; do not rely on a subagent to produce faults.
Plan edits: add WP `M0-RP` (Claude, 6-10 h, S1, ahead of M1 in the chain); add `agent-roleplay` to the 1.1 status vocabulary; S-MAP-lite uses it; M1 (Ollama/local model) moves off the T0 critical path to a parallel item still needed for M3 repeatability and zero-cost CI. T0 serial depth falls from 22-32 h to about 14-22 h.
