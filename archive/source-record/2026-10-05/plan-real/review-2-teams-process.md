Scope: section 5 (ownership, hand-offs, protocol, file transfer), 4.2 (capacity), 7.2 (asks), DEBATE-2, DEBATE-6. ## 1. Verdict (5 lines)

1. The split is directionally right (Codex cannot reach Podman, live PG or live Core, so it cannot verify seam code) but it is NOT real as written: three inherited facts are wrong or stale (Codex "has no GitHub", "K2 implements the existing writer port", "shared cargo registry"), and one section reverses an accepted two-team agreement using a silence-is-consent default that the journal explicitly forbids.
2. The biggest hidden coupling: the Rust types a seam must talk to are sealed or private (`GovernedRegistryWriter` is a concrete struct, `NativeCandidateRegistryReadbackPort` and all of `run_timeline_v2` are `pub(crate)`), so "Claude writes new crates and touches nothing of Codex" is false; E9 and K3 need Codex-side API changes.
3. Putting the new crates in the root workspace breaks Codex's own gate (`clippy --workspace`, `test --workspace`, offline) and makes Cargo.lock the collision point; a separate seams workspace removes both problems.
4. Claude has no Rust record (journal: "no Rust touched" on every Claude PR; Python 31k lines vs Rust core 43k lines), and about 180-200 of the 185-260 T0-T1b hours sit on Claude-owned Rust; review overhead is underestimated (observed 40-60% rework, plan says 15-25%).
5. The user asks can be cut from 11 to 3 blocking ones; the tripwire is placed one session too late for the riskiest seam (E4/E5 lands in S3, tripwire is end of S4); early AWS should be asks plus offline plan only.

## 3. Resolution of assigned DEBATE items

### DEBATE-2: who owns the PG job-store adapter and worker while Codex is frozen
Decision: Claude owns the PG implementation and the worker loop and runs all PG tests; Codex owns the trait semantics and a reusable conformance suite. Reasons and evidence:
1. `DurableJobRepository` (durable_jobs.rs:111) and `quota_grant`/`RunConfig` already fix the semantics in Codex code, with 18 reducer tests; an adapter adds SQL and concurrency, which only a live PG can prove (leases, SKIP LOCKED, fencing, lost NOTIFY).
2. Codex cannot execute any PG test: its last two validations record "PostgreSQL destructive tests were not enabled / Podman unavailable" (CX-0171, CX-0183); all six existing PG tests are `#[ignore]` and ran only in hosted CI (now dead). Blind SQL with a user-mediated relay costs a full round trip per defect.
3. T1b is a serial chain of 25-35 h behind this adapter; any Codex latency lands on the critical path.
Mechanism: (a) Codex writes `pub fn repository_conformance<R: DurableJobRepository>(make: impl Fn() -> R)` in `crates/core` (pure, run on `InMemory` by Codex offline, adds two-claimer, lease-expiry, stale-fence cases as properties); (b) Claude writes `seams/pulso-pg` implementing the trait and running the same suite on `pulso-dev` PG; (c) migrations by Claude in the plan's 0050+ block, reviewed by Codex read-only when unfrozen. This drops D-PG from 14-24 h Codex to about 6-8 h Codex (suite) plus Claude's 10-14 h that E6 already budgets, and removes the end-of-S5 fallback date. It requires the trait to be implementable outside `crates/core` (the trait is `pub`; verify that its associated types are constructible, F4).

### DEBATE-6: S4 tripwire and early AWS slice
(a) Tripwire timing: end of S4 (about 72 focused hours in) is too late. The two real risks are K2 live against the real Core (lands S2) and E4/E5 (a Rust HTTP server that must pass the same black-box tests as the double, lands S3); a failure of the second is visible at the end of S3, not S4. F-PY is also less of a fallback than presented: the Python stand-in (`e2e-core/codex_standin`) already exists, so F-PY is the status quo plus Rust `step` subcommands, and its cost is measured in rework of E2/E3 only if the shell is dropped late. Decision: two tripwires with objective, pre-agreed criteria, no user decision call at the time: TW-1 end of S2 (K2 live: same `Idempotency-Key` twice gives one run on the real image, local-model scout receipt); if red, cut scope to `step` subcommands and stop Rust server work. TW-2 end of S3 (E4/E5 black-box suite green against the Rust server and the broker serves a real scout); if red, adopt F-PY for steps 1-5 and keep Rust semantics-only. Replace U-11 by this pre-delegation.
(b) Early AWS slice (T1-shaped, no Core, no model): not worth it before T1a. A control-api plus PG on staging with `platform_live`/synthetic data demonstrates deploy plumbing only, costs 25-45 h including the 10-18 h first-apply fix cycle plus recurring spend, and uses user attention while the user's stated goal (real Core, real model) is absent from that slice. Do instead: send the U-5 questions in S1 (latency is days), have one Claude subagent produce an offline `terraform plan` review in S3-S4 (no apply, no Rust dependency), and schedule the first apply at the T1b gate when the worker exists (continuous operation is what AWS adds). If the user wants an earlier AWS signal, restrict to "ECR push + `terraform plan` clean", not a running service.
