# Review 3 of v2-synthesis: real-ness, honesty, spec gaps, external reality

Critic 3. Scope: does each tier deliver what the user means by "real"; what the spec or the goal needs that the plan lacks; what external systems actually allow. Evidence was read, not run (spec V3, plan V3, estado-spec 00/03, journal CX 21:12Z entries, worktree main 41492cb, agent-core pin c814c2b, llm-gateway via `gh api` at `63155b6`, `pulso_muestra_e0/README.md`, PowerShell hardware queries). Nothing was edited except this file.

## 1. Verdict

1. The plan is the best of the three v1s on honesty vocabulary (`doubles[]` generated by the engine, data-class labels), but three places still allow a dishonest "real": T1a step 6 (judge suite hand-written by the lane that plants the world), T1a/T1b step 10 (effects emitted by our own simulator), and every E0 step (a 7-8B local model labelled as the discovery engine).
2. It breaches the E0 policy in its own mechanics: recorded model I/O and "corpus" files are committed to a GitHub-bound repo (M3, S-MAP, G0a/G0c). Spec 28.6, the dataset README and spec line 144 ("each repo excludes ... grabaciones") forbid that.
3. It over-restricts one thing and under-restricts another: it treats the original bank dataset like E0 (spec decision 2 at line 406 allows treated data to models, "cuidando PII"), which blocks the only path where a strong hosted model on real data is permitted; and it enforces the E0 rule by test and policy file instead of by construction.
4. It silently redefines "continuous". Spec 28.4/28.5 define continuous as the prequential replay protocol (frozen vs continuous, replay clock, cohorts, evaluator-only labels). The plan has none of it; its "continuous" is a scheduler plus queue.
5. DEBATE-3: no. DEBATE-4: local 12 GB GPU is enough for a 7-14B model, fallback ladder in section 3. DEBATE-5: seeded base world yes, seeded mechanism metadata no.

## 3. Resolution of assigned DEBATE items

### DEBATE-3: may treated, aggregated, marker-substituted E0-derived payloads go to a hosted model?

Decision: **No, for any payload derived from E0 content, including aggregates, without a new written authorization from the user.** The strict position (B, C, spec) is correct; A's carve-out for "aggregated payloads" is not supported.

Decisive text:
1. README of `pulso_muestra_e0` last line: "Solo para participantes del hackatón. No lo publiques ni lo envíes a servicios externos." The README rule is on the package; a hosted model is an external service.
2. Spec 28.2: "La autorización del usuario cubre procesar E0 en local y servicios locales controlados ... no publicar el paquete ni transmitirlo a proveedores remotos. Por ello RunConfig bloquea egress remoto con contenido E0, sin bloquear su lectura/proyección ni el uso de servicios locales." The block is on "contenido E0", not on rows only.
3. Spec 28.6: "El runtime de descubrimiento E0 debe usar adapters/provider replay locales, sin transmitir filas, texto, prompts ni derivados identificables fuera del host/stack local. Smoke live de modelos emplea fixtures independientes permitidos, no conversaciones E0 enmascaradas." The last sentence is the closest to the question: even masked E0 conversations are explicitly not allowed as live-smoke material.
4. Honest nuance: "derivados identificables" leaves room for non-identifiable aggregates literally, and A reads it that way. The room is not usable: (a) a scout or builder prompt cannot be built from pure counts, it needs treated turn text and case refs (28.3 scout works on "texto tratado y SQL"); (b) "markers substituted" (`{NOMBRE}`, `{MONTO}`) are what 28.6 calls masked conversations; (c) the runtime guard cannot tell aggregate from identifiable at send time, so the rule must be content-class based; (d) the user's decision (2) in spec line 406 is about the original dataset with PII care, and 28.6 was written afterwards (audit 01-10-2026) specifically for E0.
5. What would change this: a written user statement (and, if the hackathon rules require, the organizers' consent) that named aggregate classes may leave. Until then E0 stays local.
6. Consequences: no hosted `builder_design` on E0 ever; the E0 demo is local model only; hosted real-model evidence comes from `original-treated` (H2, needs U-9) and `synthetic`. AWS carries no E0 under any tier (matches the plan), and neither do model recordings (B1).

### DEBATE-4: local-model quality floor and honest fallback for `builder_design`

Hardware facts (read-only): RTX 3060 12 GB VRAM (1.3 GB used by the desktop), 6C/12T CPU, 16.9 GB RAM with 5.7 GB free while Podman and agents are loaded; no model runtime installed. Estimates below are from general knowledge, unmeasured on this machine; the probe in H6 replaces them.
- Fits comfortably: 7-8B Q4/Q5 (about 5-6 GB weights) with 16-32k context, roughly 40-60 tokens/s on this GPU class. 14B Q4 (about 9 GB) fits only with about 8k context; with 16k the KV cache pushes it past 12 GB. 30B+ does not fit without CPU offload, which is too slow with 5.7 GB free RAM and the Podman VM resident.
- Pipeline budget: builder_design at roughly 2-4k output tokens takes about 1-2 min on a 7-8B and 2-3 min on a 14B per attempt; with two regenerations acceptable for a T1a thread, not for loops.
- Quality risk: the gateway only offers `prompted` structured output validated after the fact; small models fail on nested schemas and on long context. The existing Codex lane already treats builder output as "untrusted design intent" (journal, E0 builder lane), which is the right shape for a small model.

Honest fallback ladder (fixed in advance, with labels):
1. Reduce the task, not the label: make `builder_design` output a flat design-intent object (the Codex lane shape: target kind, operation, rationale, evidence refs) and let Rust expand it into ChangeSpec; keep the schema inside the gateway subset; temperature 0; one in-schema regeneration. Measure schema-valid rate over 20 runs on the E0 input.
2. If valid rate < 90% on 8B: try a 14B at 8k context with evidence truncated by a deterministic selector; label `local-model(14B,ctx8k)`.
3. If still below: stage result stays `invalid_output` as a first-class honest outcome (`partial`), T1a reports step 4 `local-model: invalid_output rate X/20` and the thread continues only on a candidate produced by the second path below, labelled `stand-in`.
4. Second path (not a replacement for 1-3): run the same builder on `original-treated` data with a hosted model if U-9 allows (H2). This yields a real strong-model step 4 without touching E0, and is reported separately.
5. Do NOT use "recorded replay of real hosted output on a synthetic twin" as a fix for E0 steps: it relabels a different dataset as E0. Replay is fine for CI determinism of the same-class corpus (synthetic only, B1).
Plan impact: gate T0 on scout only is too weak; add to T0 acceptance the builder_design schema-valid rate (>= 9/10 or a recorded miss), so the quality floor is known at S2, not S4.

### DEBATE-5: evidence-bound builder output vs seeded catalogue with decoys

Decision: **A seeded base world counts as real only for what it is (the "before" state the improvement is applied to); a seeded mechanism catalogue that pre-links findings to targets does not count as a real step 4, and must be labelled `mechanism_proxy / seeded_target`.** The cheapest honest design is hybrid and starts with Add, not Replace.

Exact sentences:
- Plan V3 section 2: "La magia no consiste en animar un resultado precargado."
- Spec 28.1: "No fijar las disputas como ganador global ni hardcodear SIG-001/SIG-002 como salida del detector."
- Spec 29.5 table header "Evidencia enriquecida descubierta, no precargada" and the sentence "ToolDef sin implementación no resuelve nada" (a candidate needs executor and permission dependencies that really exist).
- Spec 28.3: "Hallar oportunidades nuevas es resultado permitido ... sin exigir pertenecer a las tres señales preparadas."
- Spec 28.5 E0-D: "E2E oportunidad→EntityDraft→gates; error humano repetido no se acepta por coincidencia; ... propuesta nueva fuera de referencias se evalúa sin rechazo automático".
- Journal CX 2026-10-03T21:12Z: "To preserve the success criterion without hardcoding a complaint/mapping, the next critical slice must let an investigation/builder use the signal evidence to propose one or more Agent Core-native artifacts (likely a new or revised Flow) ... An unlinked outcome must remain honest until that autonomous artifact is generated and read back."
- Spec 28.4: "Un log grabado por sí solo no es banco stateful ni prueba contrafactual ... o declara mecanismo proxy/no evaluable."
- estado 00 section 4: "What would make the demo dishonest: ... a mapping keyed to the winning category."

Reading: a catalogue of existing Core artifacts (flows, tools, agents the platform already has) is the base state the builder reads through `ReadBase`; that is legitimate and required, since a Replace needs something to replace and Core must hold the executor. A catalogue whose entries carry "mechanism metadata" matched against the finding is the preloaded answer in another form: even with decoys, the matcher selects the target, not the model, and the world author knows which decoy is the target. Decoys prove the matcher is not keyed to a name, not that the system discovered anything.

Concrete rule:
1. Step 4 label: `real` only if the target and operation come from builder output validated against `ReadBase` and evidence (no metadata matcher decides). `mechanism_proxy` (and `unlinked` when ReadBase has no fit) otherwise.
2. The seeded world is allowed, with `base_world=seeded` and the author/author-separation record (B2). Catalogue descriptions may state what an artifact does (its behaviour), never which findings it answers.
3. Required tests: renaming or permuting categories changes support not routing (already in plan); a finding for which the world holds no suitable base must produce an `Add Flow/ToolDef` proposal or `unlinked`, never a forced Replace; a second finding on a different mechanism (not designed into the world) must run through the same path.
4. Start with Add (K3 already lists Add ToolDef) because it needs no pre-seeded target and matches the CX 21:12Z phrase "likely a new or revised Flow"; Replace follows when ReadBase exists. S-MAP should test builder-only first (as plan 9.3 does) and keep the catalogue as the labelled fallback, as the plan proposes, but with the label rule above rather than a product-call ambiguity.

## 6. The three changes that most improve feasibility and efficiency

1. **Add a "data class gate" in session 1 that settles H2/H3 and B1 once**: two compose profiles (`e0-local` internal network, local alias only; `hosted`), a pre-push content scanner, split corpora, and the single ask U-9 (original dataset to hosted models? E0 row text readable by hosted agents?). This costs about 6-8 h, removes the only policy risk in the plan, and unlocks a strong-model real path on `original-treated` data at T1a, which is the biggest single gain in "real".
2. **Run the model probe first (1-2 h) and gate S-MAP on it, with the flat design-intent builder output**: it converts the weakest assumption (7-8B builder quality) into a measured number before 6-8 h of S-MAP and 10-16 h of M3 are spent, and fixes the fallback ladder in advance.
3. **Insert author separation and honest step labels as tests (G1) before the first thread**: the second gate verdict and step 10 are `simulated` until the effect and suite are authored by another agent and sealed first. That one change prevents the single failure the user fears most (a polished demo whose improvement is circular) and costs about 4 h on top of G1.
