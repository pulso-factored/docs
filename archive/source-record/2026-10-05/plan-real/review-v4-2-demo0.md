1. `pulso_muestra_e0/reportes/SAMPLE.md` line 3: E0 is generated by `synthetic/platform_sample.py` with design assumptions. "Real E0 package" should read "real engine on the E0 generated sample"; the engine discovering what the generator encodes is discovery relative to the engine, but not evidence about real customers. 2. The sensor family is ONE recurrence metric (plus a tool-retry descriptive metric). "Existing sensors ... one family" in the plan is accurate; "signals" plural in DEMO-0 prose should say one admitted signal and recorded discards.
3. The E0 finding has no exact route to a Core artifact (`unlinked / no_exact_supported_flow_mapping`, estado-spec 03 row 4, `e0_mechanism_resolution.rs:571`). v4 handles this by letting a roleplay builder choose the target and accepting `unlinked`/`not_evaluable` endings. That is honest only if the target choice is derived from a catalogue of capabilities in ReadBase, not from the model's narrative: with a Claude subagent as builder, the mutation test "winning category changes with the label" no longer constrains the mapping. Fix F6.
4. Building the runner needs a first cargo build of crates/core (about 60k lines, bundled sqlite) on a host with about 1.7 GB free RAM; budget it inside ED0 (v4 says "the one cargo action"), and use a separate target dir.

## 3. Roleplay design versus the real code

Verified facts:
- llm-gateway (main, README, .env.example): `POST /v1/generate` with `prompt` (system, verbatim), `inputs` (RFC 8785 JSON in the user message), optional `schema` (closed subset: type, enum, properties, required, additionalProperties boolean, items; others -> 400), `profile` {endpoint_alias, model, temperature, max_tokens, timeout_s default 8 max 300, structured native|prompted, price}. Auth: per-consumer Bearer via `GATEWAY_CONSUMERS` + `GATEWAY_TOKEN_*`. Aliases: `LLM_ENDPOINTS` {alias: {base_url, api_key_env}} (so the shim as an OpenAI-compatible base_url with a dummy key is legitimate). No retries, one deadline, 1 MiB body, typed errors, usage from the provider (`usage_known`).
- agent-core pin: `HttpLLMGateway.generate` posts to `<url>/v1/generate`, client timeout = `profile.timeout_s + 5`; the agent node uses `LLMAgentPort` which runs in `prompted` mode with a flat STEP_SCHEMA `{kind: tool_call|final, tool, args, output}`; it explicitly says "sin tool-calling nativo". The Core tool loop (execute tool, append observation, next call) is agent-core's, per step, with `max_steps` 16 in the three agent flows.
- core-bridge: `PULSO_LLM_STAGE_POLICY` pins alias, model, price and max_tokens per stage and rejects a registry profile that differs (`alias_mismatch`, `model_mismatch`, `price_mismatch`); `AsgiCoreClient` timeout 600 s for the whole run call; after that the receipt becomes `unknown` and goes to reconcile.
- The e2e stack's LLM double already speaks the gateway protocol (`/llm/v1/generate` in fixtures_app); the live tests already drive real agent-core through HttpLLMGateway against it.

Findings:
- R1 (HIGH). Plan sec 3.3 says the shim returns OpenAI `tool_calls` and "Core executes them". Wrong: the gateway sends a plain chat completion and expects JSON text; tool use is the model's JSON `{"kind":"tool_call","tool":"pulso/lab_query@1.0.0","args":{...}}` in content. The shim only has to return `choices[0].message.content` as JSON text plus `usage`. Simpler than described; remove the tool_calls round-trip from M0RP acceptance and replace it with "JSON step round trip".
- R2 (HIGH). Alias/model/price: v4 says alias `roleplay`, model `agent_roleplay@1`, price 0. The registry profile `pulso-evolution-structured@1.0.0` has alias `pulso-evolution-llm`, model `external-reasoning-model`, price 1/4, `timeout_s: 60`, `structured: prompted`. With the stage policy active these must match, and changing a profile changes release digests (manifest, expected-state, check-digests). Cheapest correct design: keep the registry untouched, configure the real gateway `LLM_ENDPOINTS` alias `pulso-evolution-llm` pointing at the shim, and let the shim echo whatever `model` string is configured. If M1 truly wants alias `roleplay`, add a profile-bump WP with the digest cascade.
- R3 (HIGH). Timing: the profile `timeout_s: 60` caps every model call at 60 s (the gateway returns `timeout` and agent-core fails the step), contradicting the plan's 20-90 s responder latency and its "120-300" assumption. And the whole scout stage is bounded by the 600 s invoke timeout, while v4's own estimate is about 15 scout calls at 20-90 s (5-22 min). Live scouts will hit 600 s unless (a) the stage profile `timeout_s` is raised to 120-300 (asset bump, 2-3 h inside M3), (b) DEMO-0 prompts cap the scout at 5-7 steps (the asset says max 16; the responder can finalise early, make this an RPP rule), and (c) the Core client timeout is made configurable (a small L-BRIDGE change, 1-2 h) or the stage uses the existing `unknown` -> reconcile path knowingly. SNET (2-3 h) is where this is measured; add it to the SNET acceptance.
- R4 (MEDIUM). Call count: scout up to 16, verifier up to 16, builder up to 16 per the flows, plus writer (deterministic tools, no model per the Core flow) and the evaluation arms. The plan's 40-60 calls is plausible only with the step caps of R3; otherwise 48+ before arms. Latency per live run 15-90 min is consistent only under the caps.
- R5 (MEDIUM). Digest-keyed replay: the request body carries `labels` with run_id, turn_id, session_id (random per run) and inputs with binding/job/artifact ids; a raw-body digest will miss on every re-run. Key on (stage, step index, digest of canonical inputs with volatile ids and labels normalised); acceptance of M0RP/M3 should include "same run replayed 3 times from a fresh Core DB, 0 misses". Without deterministic ids this is the largest hidden cost of replay.
- R6 (MEDIUM). Treated-payload scanner feasibility: feasible as a deny-by-default allow-list over named input paths (goal, step, tools catalogue, output_schema, observations with typed fields) because the stage input is structured (`LLMAgentPort.step` builds a fixed dict). The hard part is the observations: tool results from `lab_query` are derived from raw E0 and the plan's own data-class table forbids "derived extracts" for third parties. TPS must therefore specify which lab aggregates are treated (counts above a k threshold, hashed ids, no free text) and ED0L must produce only those. Without that, either the scanner rejects every scout step or the allow-list quietly admits derived text. Add this to TPS acceptance ("a lab row with free text is rejected; a k-anonymous aggregate passes").
- R7 (LOW). The gateway M1 build needs a Go toolchain image in Podman (Dockerfile, Go 1.27 per README); confirm in SNET that the base image is pullable offline or that the user approves the pull (it is a download).

## 5. DEMO-1..3 progression

- Host axis: S1 Python -> S2 Rust steps called by Python (DEMO-1a) -> Rust shell run-once (DEMO-1) -> PG worker, kill -9 (DEMO-2) -> AWS staging (DEMO-3): coherent, each re-runs the same thread through the same ratchet file, `host` recorded per step. Retirement gates RG-1..RG-5 are objective.
- Model axis, defect (HIGH): GT05 deps include SMOKE, which needs ENV9 (local GPU model, download approval U-14b) and M1; GT1A and GT1B depend on GT05. Plan sec 15 says "none blocks the demo path" and the default for ask 4 is "none downloaded", so under silence GT05, GT1A and GT1B cannot pass. Also GT1A's acceptance says "E0 run with data=E0 and local model only". Fix: split GT05 into GT05 (host/semantics, no model) and GT05m (model rung-up, needs ENV9/U-14b); GT1A/GT1B depend on GT05 only; the E0 local-model acceptance moves to GT05m and a documented fallback is "roleplay replay".
- Ordering: AWS before breadth (DEMO-3 before GT2/GT3) is sensible because AWS depends on GT1B, not on breadth, and the breadth lanes run in parallel; the user's "real infra" clause is served earlier than breadth.
- Product axis: real inbound only at T3 (P3); acceptable given Product Phase 1 has no AI features.
