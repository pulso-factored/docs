## 0. The thesis in six lines

1. The missing piece is ONE chain, not many gaps: a long-running Rust process that talks to the real Core runtime, a real model and the real platform data model. Everything Python-side exists and is exercised today only through a stand-in engine.
2. Build the thinnest honest chain first (a narrow slice of each of the 10 demo steps, every slice REAL, none scripted), then widen in tiers. Breadth (13 families, Jev, DuckDB, AWS) never delays the first end-to-end thread.
3. Retire the biggest unknowns in sessions 1-2 as timeboxed parallel spikes: (a) Rust to real Core client, (b) a real model through the real llm-gateway, (c) E0 finding to Core artifact mapping, (d) Rust-served lab broker + ingest endpoint. If a spike fails, the plan changes in session 2, not session 8.
4. Claude takes the main thread INCLUDING new Rust crates (disjoint from Codex's files); Codex, once unfrozen, hardens and extends the libraries it owns and is the independent adversarial reviewer of Claude's Rust. This removes the single point of failure (Codex frozen, no GitHub, no Podman) without reorganising the repo.
5. Every tier ships a demo that is honest by construction: a `doubles[]` report per run generated by the system itself, plus a label vocabulary (1.2). A scripted piece is allowed only if listed.
6. Headline: T0 "real wire" in about 2 sessions; T1 "thin thread, steps 1-10 real in narrow form" in about 6-9 sessions (medium-low confidence); T2 "durable, adversarially honest" about 11; T3/T4 in parallel to about 16-18. See section 7.

### 1.2 Honesty vocabulary (every report line carries one)

`real` (real dependency, real data path, engine-driven) / `real-narrow` (real, one family/kind/path) / `stand-in` (real downstream, driven by Python or fixtures) / `simulated` (synthetic, incl. scripted human) / `blocked` (named dependency). The run report is generated by the engine from observed facts (which URL answered, image digest, Core `/internal/v1/version`, gateway `model` echo), never hand-written. A test fails if a step claims `real` while any receipt's provider is `scripted`.

### 2.2 Real critical path (not the nominal one)

Nominal view: "the Rust Core client is the gate". After splitting, the chain is `RC-1 (9) -> RC-3 (14) -> EV-1 (16) -> EV-2 (12) -> HA-1 (12) -> PD-3 + MEM-1 (10) -> QA-1 (12)` = about 85 focused hours serial; after splitting RC-3 (draft / writer), EV-1 (suite / queues), HA-1 (port / state) the serial depth is about 50-60 hours = 5-7 sessions. Two hidden gates sit OFF that chain and are the usual killers:
1. DM-3 (E0 finding -> exact Core artifact) is intellectual, not plumbing; if it fails EV-1 has nothing to evaluate. Hence the session-1 spike with a predefined fallback.
2. Real-model behaviour: stage prompts and schemas proven with a scripted gateway may fail (`invalid_output`) on a real model. Hence MG-1/CA-1 in session 1.

## 4. Parallelization design

### 4.1 Lanes with disjoint file ownership

| Lane | Owner / agents | Owns | Never touches |
|---|---|---|---|
| L1 core-client/compiler | Claude subagents A (+B) | `crates/core-client/**`, `crates/core-compiler/**` | `crates/core/**` |
| L2 engine runtime | Claude subagent C | `crates/pulso-engine/**`, `migrations/0006+` | migrations 0001-0005 |
| L3 control-api and broker | Claude subagent D | `crates/control-api/**`, `contracts/control-api/**` | engine internals |
| L4 discovery and gates | Codex lane 1 | `crates/core/src/e0_*`, `platform_*`, `signal_*`, `evaluation_plan.rs`, new `improvement_evidence.rs`, `crates/runner/**` | Claude crates |
| L5 memory/lab | Codex lane 2 | `memory_*`, `local_lab.rs`, `wiki_scratch.rs`, `sandbox.rs`, 0005 | Claude crates |
| L6 Python bridge/assets/stack | Claude subagent E | `core-bridge/**`, `agent-core-assets/**`, `local/core/**`, `bridge-contract/**`, `platform-*/**`, `e2e-core/**`, `demo/**` | Rust |
| L7 console | Claude subagent F | `debug-console/**` | all else |
| L8 infra | Claude subagent G (T4) | infra repo `terraform/**`, `release/**` | engine repo |
| Root integrator | Claude orchestrator only | workspace `Cargo.toml` members (additive), `local/compose.yaml`, `scripts/dev.ps1`, `.github/workflows/*`, docs index | n/a |

Rule: Claude's new crates depend on `crates/core` as a library; an API change needed there is requested in the journal and made by Codex, or by Claude as a small additive `pub` change that Codex acknowledges (silence for one session = accepted, default to proceed).

### 4.2 Subagents inside each lane

Implement -> independent adversarial review by a different agent (1-3 loops) -> consolidate. Author and judge differ for RC-3/EV-1/EV-2 (the candidate author never edits baseline, oracle, thresholds). Max 4 Claude implementers + a reviewer pool; the orchestrator re-checks saturation every 15 minutes. Heavy Podman suites run one at a time per machine (`pulso-dev` is Claude's); the orchestrator schedules the slots.

### 4.3 Contract hand-offs: who publishes what first

1. Already published (Claude): `bridge-contract/` (OpenAPI, goldens, conformance), `platform-contract/`, ADR 0011/0012. Rust codes against these.
2. Session 1, Claude (ER-0): `contracts/control-api/openapi.yaml`, broker confirmation, `contracts/thread/` report schema. Exporter, console, bridge conform before the server exists (mock first).
3. Session 1, Claude (CA-2): `capability_manifest` schema. Codex's DM-3 resolver consumes it; Codex confirms in the journal within one session or accepts by silence.
4. Session 2, Codex: `ChangeSpec` and `ScenarioCase` JSON schemas + goldens under `contracts/engine/` (serialized from existing Rust structs). Claude's EV-1/RC-3 and assets consume them.
5. Session 3, Claude: `ImprovementEvidence`/gate result shape for the console.
6. Contract changes are additive; a breaking change = new version file + journal entry.

### 4.4 Codex scope (user decision; proposed text)

Lift CX-0180 for: (a) L4/L5 work above; (b) adversarial review of Claude's Rust branches read from disk (no GitHub needed); (c) no Podman use until a `pulso-codex` machine exists: pure-Rust, sqlite and in-memory tests only. Codex never edits Claude lanes; Claude never edits L4/L5 files except the additive `pub` exports in 4.1.

### 4.5 Merge cadence and worktrees

Three Claude worktrees (rust-thread, py-bridge, infra), at most two Codex. Consolidated PRs at tier milestones (PR-T0, PR-T1a engine+client, PR-T1b gates+human+thread, PR-T2...), stacked branches, never waiting for a merge; the user merges in batches. Local CI (`verify-local-ci.ps1` extended by QA-4) is the pre-PR gate; each PR body carries the evidence report (commands, counts, SHA, doubles).

### 4.6 Cheap coordination protocol (shared journal only)

Entries only on four events: contract published/changed; branch/PR opened/merged; blocker + default taken; tier gate result. Format: `UTC | TEAM | ID | event | reply-to | action requested | default if silent`. No reply within one session = accepted. Worktree and Podman ownership declared once at start.

### 4.7 What each side does while blocked

- Claude blocked on a Codex lib change: continues Python/console/infra lanes; the stand-in stays only as a regression twin.
- Claude blocked on the user (key, AWS): local small model; Terraform plan only; docs/ADR/CI lane.
- Codex blocked on Podman: libraries, schemas, property tests, review of Claude branches, pure DM/EV logic.
- Both blocked on agent-core or Product: keep the capability profile and `blocked` labels; widen negatives and fixtures.

## 8. Tier pass criteria

A tier passes only if: (1) the run report lists every step with a 1.2 label and the engine-generated `doubles[]`; (2) the tier's negative and unhappy-path tests pass locally with real PG16 and the real Core image; (3) an independent reviewer (different agent/team) signs off in the journal; (4) docs and ADRs (sqlite lab, Jev absence, simulator source, each deviation) are updated in English; (5) nothing relies on a merge.
