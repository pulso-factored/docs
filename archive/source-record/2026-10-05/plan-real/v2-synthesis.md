Role: SYNTHESIZER of v1-A (thin vertical thread, cited "A"), v1-B (deployable and operable, "B"), v1-C (risks and two-team parallelism, "C"). Ground truth: estado-spec 00 (read in full) and the facts the three plans cite from 01-03, the journal and `gh api` reads of llm-gateway. ## 0. The plan in twelve lines

1. The gap is one chain: a Rust process that talks to the real Core, a real model through the real llm-gateway, and the real platform data model. Everything Python-side exists and is exercised only through a stand-in engine (estado 00 section 3).
2. Backbone (decision 1): tiers from A (thin vertical thread first, every step real but narrow), lanes and coordination mechanics from C, data tier, cost, ops and AWS items from B.
3. First action (decision 3): a time-boxed spike S-MAP (E0 finding to a real `builder_design` stage on a real or local model to a Core artifact via dry-run) because it is the only intellectual unknown, in parallel with the `core-client` crate.
4. Split (decision 2): Claude writes the new seam crates (core-client, control-api, engine/executor shell) and is the single integrator of Cargo, CI and compose. Codex keeps pure domain semantics in `crates/core`, tested offline against goldens that Claude publishes. This overrides plan V3 section 5 and needs user and Codex consent (ask U-2).
5. Durability (decision 4): every stage is a `JobHandler` from day one; first run by a run-once executor with no tokio; a minimal PG-backed queue and worker lands in T1b, never later than T2. Tripwire at end of session 4: no live Rust shell on the real Core means fallback F-PY (Python shell over the pure `pulso-engine step` CLI).
6. Data rule (decision 5, B section 8, C F-3, spec 28.6): E0 and bank CSVs stay on the local host. Discovery on E0 and any real model on E0 use a LOCAL model behind the gateway. Hosted models only on synthetic or Product-authorized data. Therefore a continuous AWS system runs on `platform_live` or synthetic data, never on E0. This changes what "real" means per tier (section 1.3).
7. Cost control lives in our runtime (decision 7): provider-key hard cap, per-run and per-day ceilings, kill switch. No Jev in the first threads (`llm_structured`).
8. AWS (decision 6) is user-gated and runs as a parallel track; everything is validated locally on Podman first; release is a local script, not GitHub Actions.
9. Product platform (decision 8): Phase 1 data only; insight stops with no Core target; the loop closes through simulator release events. Phase 2/3 are gated on Product.
10. Honest totals: T0 through T1b about 185-260 focused hours (about 55 hours of serial critical depth); everything through T3 plus AWS about 480-740 hours. Section 8 reconciles this.
11. Minimum viable cut: section 8.3.
12. Six items could not be resolved and go to the debate round: DEBATE-1 through DEBATE-6 (section 10).

## 1. Definition of "real", by tier

### 1.1 Honesty vocabulary (shared by every tier)

Every step line of every run report carries one status, one data class, and the report carries a `doubles[]` list generated BY THE ENGINE from observed facts (URL that answered, image digest, Core `/internal/v1/version`, gateway `model` echo, provider field of each receipt), never hand-written (A 1.2, C section 1). Reports live in `contracts/engine-run/` (schema published by Claude in session 1) and carry `target`, `sha`, `contract_revision`.

| Status | Meaning |
|---|---|
| `real` | real dependency, real data path, engine-driven, full family or kind coverage promised by the tier |
| `real-narrow` | real dependency and path, one family or kind or path only |
| `local-model` | real model, but a small local model; quality claims forbidden |
| `recorded` | replay of a previously recorded REAL response (provenance, date, digest); never shown as live |
| `stand-in` | real downstream driven by Python or fixtures |
| `simulated` | synthetic source or scripted actor (simulator, sandbox issuer as human) |
| `blocked(<dep>)` | named external dependency (Jev PR #28, CAP-41 bank, CAP-44 IdP, Product Phase 2) |

Data class label on each step: `data=E0-local`, `data=synthetic`, `data=product-authorized`. Honesty tests (they bite, A WP-01): a report that claims `real` while any receipt provider is `scripted` fails; a step with `data=E0-local` whose receipts show a hosted provider fails; a mapping keyed to the winning category fails the mutation test (rename or permute the category, mapping must not move).

### 4.2 Assumption behind "session" (stated once, used everywhere)

A session is one orchestrated block of about 8 wall hours: Claude orchestrator plus 3-4 Claude implementer subagents plus one independent reviewer, and 1-2 Codex agents if unfrozen; never more than 5 agents active (machine cap), one cargo slot, one Podman E2E. Effective throughput is about 18 focused agent-hours per session (band 12-24), not the 25-30 a naive agent count suggests, because the one cargo slot and one Podman machine serialize the heavy work (C section 5.2, X-05). Serial critical depth per session is about 7 hours. If Codex stays frozen throughput drops to about 14 and D-* packages move to Claude (section 7, U-1 default).

### 5.4 Cheapest reliable protocol (shared journal only)

1. One stanza format, at most 8 lines, tag first: `[CONTRACT-PUBLISHED id@rev path digest]`, `[CONTRACT-CHANGE id reason migration]`, `[ASK from to need-by default-if-silent]`, `[DEP-ASK crate version reason]`, `[BLOCKED wp reason default-taking]`, `[DONE wp evidence-digest]`, `[HANDOFF branch head manifest]`, `[FINDING severity ref]`. Long reasoning goes to `docs/journal/*`.
2. Default-if-silent is mandatory in every `[ASK]`. Silence for one session means the default is taken, so no team idles.
3. Read protocol: start each session with the last 20 journal headings filtered by tag; nobody reads the 350 KB journal.
4. State table: the first stanza of each session is a 10-row table (WP, state, evidence, next, blocker, default). It is the only status report. Blocked agents are not counted as active lanes.
5. Every `[DONE]` needs a receipt with target, sha and `doubles[]`; no percentage reporting (C X-16).
6. Relay to the agent-core, gateway and Product humans always through the user, in one consolidated message.
