# Plan v3: from today's state to a real, durable, continuous Pulso system

Status: final plan after the debate (v1-A/B/C, v2, four adversarial reviews, user directives). Single document; it supersedes v2 and does not patch it. Baseline: improvement-engine main 853b029 (PR #93, Codex consolidation), agent-core pin c814c2b, llm-gateway main 63155b6. Nothing here was executed or re-measured by the author; every "exists" claim is inherited from the reviews' read-only evidence and carries a falsifier in section 17. Hours are focused lane-hours (implementation, own tests, one review loop); ranges are about 80% bands; English throughout.

## 0. Goal restated (faithful paraphrase of the user's request)

Not the 24-hour scenario. Implement incrementally, aiming to reach as early as possible a REAL system that integrates with (1) the real product platform (the support and case-management platform of the Product team), (2) agent-core with its capabilities and execution, (3) the real infrastructure, and (4) the real llm-gateway; it leverages both the initial dataset and the augmented dataset (E0). The system is a durable, continuous engine, really running: it takes that data, searches for signals, analyses them to find problems and opportunities, and from there enters a loop that generates improvement proposals as agent-core artifacts (tools, flows, compiled trees, agents, Jev decision models, or any combination), passes them through agent-core, executes them for real with real models, and interacts with the product: the real "magic demo" experience written up in the spec. The plan must take everything still missing per the spec, and what is not even specified, and say how to group it, prioritize it and run it in parallel with subagents and with the other team (Claude takes the main thread, Codex supports the rest). It was reviewed in several passes, backward chains and debates with other agents until feasible and efficient (section 18).

## 2. Definition of "real"

### 2.1 Honesty vocabulary

Every step line of every run report carries one status and one data class; the report carries `doubles[]` generated BY THE ENGINE from observed facts (URL that answered, image digest, Core `/internal/v1/version` and manifest digest, gateway `model` echo, provider field of each receipt), never hand-written. Reports live in `contracts/engine-run/` (G1) and carry `target`, `sha`, `contract_revision`, `host` (`python` or `rust`).

| Status | Meaning |
|---|---|
| `real` | real dependency, real data path, engine-driven, full coverage promised by the tier |
| `real-narrow` | real dependency and path, one family, kind or path only |
| `local-model` | real small model on our hardware or infra; quality claims bounded by the measured schema-valid rate |
| `agent_roleplay` | real HTTP path, real gateway, backend answered by role-playing subagents; plumbing and mapping logic only, `quality_claims: forbidden` |
| `recorded` | replay of a recorded response keyed by request digest, with provenance; never shown as live |
| `stand-in` | real downstream driven by Python host or fixtures (for example `host=python`) |
| `simulated` | synthetic source or scripted actor (simulator, sandbox issuer as human) |
| `blocked(<dep>)` | named external dependency (Jev PR #28, CAP-41 bank, CAP-44 IdP, Product Phase 2) |

Honesty tests (they bite; owner G1): (1) `real` while a receipt provider is `scripted`, `agent_roleplay` or `recorded` fails; (2) data class E0 or CSV whose receipt shows a third-party provider (hosted, or `agent_roleplay`) fails unless the run config carries `third_party_ok:[E0]` with a journal reference to the user's sentence; (3) a mapping keyed to the winning category fails the rename/permute mutation test; (4) per-port Core double provenance (tool dispatcher, authz, classifier, calibration, transcript, grant, budget resolver) and model price source (`placeholder` vs `contracted`) are listed, and a template-fallback stage output fails; (5) author separation: world, suite, simulator effect and judge carry `author` fields and the suite is sealed before the candidate exists; (6) a report with `host=python` cannot carry a T1a or later label; (7) scout and verifier use distinct actors and different model identities; (8) a tracked file containing E0 markers or a `data=E0` receipt body fails the push scan (DC0).

### 3.3 The roleplay gateway (M0RP, user idea, accepted with rules)

- Design: `roleplay-llm` shim exposes OpenAI `POST /v1/chat/completions` and `/v1/models` behind the real gateway (alias `roleplay`, model `agent_roleplay@1`, stage policy price 0). Each request (system = Core stage prompt, user = canonical inputs, tools, schema hints) is written to a queue directory with its digest; the shim long-polls under the gateway `timeout_s` (120-300) until a response file appears; Core's invoke client timeout is 600 s, so no gateway or bridge change is needed.
- Multi-turn: scout and verifier use agent nodes with tools, so the shim supports OpenAI `tool_calls` responses; the responder emits tool-call JSON, Core executes it, the next request carries the tool result. The responder is stateless per request, as a real model API is.
- Metering: the shim returns token counts flagged estimated (`usage_estimated`), else the reservation stays `unknown` (existing `metering.py`). Faults (timeout after send, 502 `invalid_output` with usage) come from a scripted side channel, never from a subagent.
- Record and replay: key = digest of the canonical request (prompt, schema, alias, inputs); second run of the same request replays deterministically (rung R2); a drift test fails with the digest diff instead of silently going live; each prompt revision costs a re-record (2-4 lane-hours). Synthetic corpora are committable; E0-derived corpora live in a git-ignored local directory with a digest manifest.
- Responder rules: a fresh-context subagent per request (or per stage batch), neither the implementer nor the reviewer of the code under test, whose only input is the queue file (prompt digest recorded); scout, verifier and builder use distinct responders; it takes ONE of the five agent slots, so live runs are scheduled in windows when an implementer is idle (section 9.2); a live run is 10-60 minutes (15-30 calls at 20-90 s); budget 4-8 live runs per session, everything else replay.
- Honesty: status `agent_roleplay`, `quality_claims: forbidden`; no lift, "discovers" or model-quality claim; a one-off local-model smoke (SMOKE, 3 of 3 schema-valid) converts it into measured evidence in T2.
- Data: synthetic only until U-13. Jev: the same shim pattern serves `/v1/jev` (gateway side exists) to test the gateway pass-through and our Rust `JevDecisionPort` (M5); the Core-side Jev node stays `blocked(jev)`.

### 4.2 Relation to the spec and the user's goal

The spec says the engine is Rust; the user's goal is a durable continuous Rust engine integrated end to end. The Python host is a labelled interim `stand-in(python)` that gets a real model path early and de-risks the three unknowns that can sink the plan (model schema compliance, E0 finding to artifact mapping, container networking) with no cargo. It is not the destination: nothing it claims counts as T1a or later (honesty test 6), and the spec amendment recorded by Claude in the journal says so. The goal is met at GT1B (Rust, durable, scheduled-ingest, real Core, real gateway) and fully only after D-REPLAY (spec "continuous").

### 4.3 Convergence: retirement of the Python host

- Freeze rule: after GT0 the Python host receives no new semantics, only glue and ratchet wiring; semantics enter only as Rust steps behind `contracts/engine-steps/`.
- RG-1 (GT05): every step the ratchet marks `real-narrow` is served by a Rust step on the Python host.
- RG-2 (GT1A): ratchet fully green with the Rust shell hosting all ten steps; for 3 recorded runs (digest-keyed replay) Python host and Rust shell produce the same ordered command/event sequence and the same `candidate_hash`.
- RG-3 (GT1A): all negatives pass on the Rust shell, including resume-after-kill between handlers.
- RG-4 (GT1B): `demo/run.ps1` defaults to the Rust host; the Python host moves to `e2e-core/legacy_host` as a regression twin, marked deprecated, deleted two sessions after GT1B. A report with `host=python` can no longer carry any label above T0.5.
- If TW-1 or TW-2 trips (section 9.8), the Python host stays the carrier with Rust `step` calls, labelled, and the user is informed; the plan is re-based, not abandoned.

## 9. Partition design for maximum parallelism

Principle: scope is not reduced; it is partitioned. 112 work packages sit in 26 lanes (16 Claude, 10 Codex). Each lane owns disjoint paths, builds against frozen contracts and fakes, and merges through one consolidation train per wave. Parallel width is limited by the environment, and the environment is a variable (E0-ENV, section 9.2).

### 9.1 Lanes and the file/directory ownership map

Every WP is in exactly one lane (column `lane` of section 8). ### 9.6 Consolidation train (methodology: consolidated worktrees and PRs, not per feature)

- Each active lane works in one worktree on `lane/<lane>/<wave>`; at most 8 live worktrees for Claude plus one integration worktree, at most 4 for Codex. Idle lanes hold none.
- The integrator (Claude orchestrator for Claude lanes; Codex orchestrator for Codex lanes) merges lane branches into `train/<wave>-<team>` in dependency order, runs the fast gate after each merge and the full gate once, and opens ONE consolidated PR per wave per team with the `verify-local-all` receipt and `doubles[]` in the body. At most 3 PRs open at once.
- Never wait for a merge: each train branches from the head of the PR that is to be merged (stacked), so the next wave starts at once; the user merges in batches (standing delegation U-8).
- Codex publishes its train through its GitHub connector; Claude trains go through `gh`. Claude-to-Codex transfer needs no mirror (both read GitHub); `git bundle` files in `D:\.codex\factored\exchange\` are the fallback for unpublished branches.

## 10. Coordination protocol between teams

1. Ownership by team: Codex owns `crates/core`, `crates/source-adapters`, `crates/runner`, the Codex migration blocks and root Cargo/CI files; Claude owns `seams/**`, Python packages, TypeScript, infra, compose, `scripts/**` and the Claude migration blocks. The only exception is lane L-COMPILE (`change_compiler.rs`, `core_task.rs`), conditional on U-2, with a `[CONTRACT-CHANGE]` stanza and Codex review. The `JobHandler` trait lives in `seams/crates/abi`; pure step functions live in `crates/core` (Codex lanes) and are wrapped by handlers in `seams/crates/engine`, so no dependency points from `crates/core` to `seams/`. Thin/thick split: Claude writes thin transport (HTTP client, servers, PG implementation), Codex writes thick adapters over its sealed types (WDX exports, composite facades' inner parts).
2. Journal: stanza tags `[CONTRACT-PUBLISHED]`, `[CONTRACT-CHANGE]`, `[ASK]`, `[DEP-ASK]`, `[BLOCKED]`, `[DONE]`, `[HANDOFF]`, `[FINDING]`, at most 8 lines each, first line with UTC timestamp and team name; each `[DONE]` carries target, sha, `doubles[]`, agent-hours, tests added, gate minutes (telemetry for recalibration). A consolidated journal entry per team about every 15 minutes while work is active; one 10-row state table at the start of each session is the only status report. `[ASK]` carries a default only where the default is safe; silence is never approval of anything touching an owner's files or the user's decisions.
3. Reciprocal review by risk class (section 11); Codex review is mandatory on JWT, idempotency, hash, fencing and egress code before any `real` label; while Codex is frozen PRs say "reviewed by Claude-independent only".
4. Onboarding brief for Codex at unfreeze (G0f, one page): current main, the pub-export list from G0g, the `seams/` rules, the lane map, migration and ADR ranges, the vendor dir.
5. Blocked behaviour: nobody idles; a blocked lane records `[BLOCKED]`, takes the documented default, and moves to the next package. Claude while Codex is frozen: all `seams/` and Python lanes; Codex libraries are path dependencies read-only. Codex while Claude is busy: pure packages and reviews against published goldens; Claude runs Codex PG and Core tests and posts receipts.
6. Humans of the agent-core team and the Product team are never contacted directly; the user relays one consolidated message (section 15).
