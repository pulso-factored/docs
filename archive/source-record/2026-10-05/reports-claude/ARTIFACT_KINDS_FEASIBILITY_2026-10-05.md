## 0. Conclusions

1. **All three are registry-feasible today, none needs a Core change to start.** Flows and tool links are the same mechanism (a new Flow version, plus for tools an `Agent.tools_allowed` entry and a re-emitted ToolDef). Policies are technically trivial and *semantically* the dangerous one: Core does not protect them.
2. **Tool "grants" are not a registry concept.** There is no tool-to-agent grant entity. A link is (a) a `tool` node in a Flow (the behaviour), (b) `Agent.tools_allowed` (declarative; enforced at runtime only for `agent` nodes), (c) deployment config outside the registry: `FieldClassifier` by `source`, `PolicyAuthz` field grants `(field, purpose)`, tool-service consumer token and principal type. The engine can change only (a)+(b); (c) must be checked as a precondition.
3. **Core's double-yardstick gate does not look at flows, policies or tool links.** It compares scenario outcomes and gate/guardrail metrics (`gate.py:26 _base_items`) and flags loosening only of the *suite* (`yardstick.py:26`). The agents have no metrics, so the only safety net is scenario coverage plus the 4 platform guardrails. Protection of flows/policies/tools must therefore be built into OUR compiler (deny-lists, dominance checks) and our guard-suite generator.
4. Recommended order: **P0 policy hypothesis (no draft), then F1 flow edit (levels 1-2), then T1 tool link (read tools only, with its flow node), then P1 tightening-only policy draft.** All sit behind the shared foundation F (ref grammar with `/`, ReadBase closure, absent-digest, cascade prediction; about 8 h, per the 10-04 plan) which new-agent and templates already partly built.

## 3. Safety: what can go wrong and what already covers it

| Risk | Core coverage | Gap | Engine guardrail (ours) |
|---|---|---|---|
| Policy loosened (500 -> 900) | none in validate; evaluate catches it ONLY if a base-suite scenario seeds a value between old and new threshold (scenario passed in base, fails in candidate -> gate fail); changing that scenario is `scenario_changed`, needs `accept_yardstick_loosened` | an agent without such a scenario (all but the pulso-min guards) | engine never drafts a value change of a policy with a human `owner`; generates boundary pair (just below, just above) as guards; hypothesis only (P0) |
| New policy / new rule node with business literal | G0-08 forces a policy ref | the policy's author is the engine | new policy = human-owned finding, never drafted |
| Flow edit skips verification or confirm | G0-05 blocks write without confirm.yes -> verify; `platform_unverified_write/_success_claim` | removing a `rule` (policy) node, rerouting an `escalate` branch, removing a read `verify`, adding a branch to `end(resolved)` all validate | compiler dominance rules: edges leaving `rule/decide/confirm/verify/escalate` frozen; no node removal; insertions must be pass-through (new node's `next` = original target); escalate reachability set preserved; node cap |
| Tool link exposes a write action | G0-05 (confirm + readback), G0-07 (agent node read/compute only), `ToolDef.accepts` (auth level/age), tool-service `min_auth_level`, advisor refused for `radicar_pqr`, principal_not_served for builder/service (`TS/subject.py:43`) | a write tool wired to a *new* confirm flow still validates; `Agent.tools_allowed` is unenforced for flow nodes | v1 links only `risk_class in {read,compute}`; write links denied (`write_tool_link_needs_human`) |
| Tool link leaks data | none in registry; `FieldClassifier` by source and `PolicyAuthz.can_read_field` are deployment config (`policy_authz.py:120`) | engine cannot see them | precondition probe: tool `source` classified, `invocable_by` includes customer/advisor, ToolDef equals `GET /v1/tools` entry; else deny |
| Green eval, tool absent | sandbox seeds replies | runtime `esc_tool` for real customers | `tool_without_executor` stays until `/v1/tools` lists it; promote is human |
| Pass without text quality | scorer reads no text | no judge in `serve` | wording stays probe/human; do not claim improvement from a native pass |

## 4. Design per kind

### 4.1 FLOW (value M-H, effort M, risk M-H)
- **Representation (structured edit script, not raw JSON).** The engine computes a *node/edge menu* from the live Flow (node ids, edges `(node,label)`, node type, protected flag, flow content digest), as it already does for text anchors. The Builder emits `{kind:"flow_edit", flow:"disputa-cargo@1", base_digest, ops:[...]}` with ops: `set_param {node, path in whitelist (max_attempts, step_up_max_attempts), value int in bounds}`, `swap_template {node, template_id_existing_or_patched}`, `insert_respond_on_edge {from,label,template_ref, kind: clarify|info}` (new node id derived deterministically `eng_<n>`), `reroute_to_existing_escalate`/`add_clarify_loop {node,label}` only toward existing non-terminal nodes. No `remove_node`, no change of `type`, no edit of `rule/confirm/verify/write/escalate` configs or outgoing edges.
- **Compile (deterministic).** Parse base Flow JSON, check digest, apply ops in order, mint ids, bump **minor** (E13: 1.1.0), rerun local prefilter (G0-02/03/05/08/12, orphan nodes, node cap, dominance: for every `rule`/`escalate` node the set of paths preserved), emit `changes[]` `{kind:"flow", content, docs}` plus predicted cascade `agent:<a>@patch+1` (E13 golden). Closed denial codes: `node_protected`, `edge_frozen`, `bypass_detected`, `unknown_template`, `locale_parity`, `node_limit`, `digest_mismatch`.
- **Suite extension (`build_suite.py`).** New mechanism `flow_branch_gap` next to `status_message_gap/closing_followup/uncovered_topic`: (a) guards generated from the BASE graph, one scripted scenario per terminal path (resolved, each escalate reason, cancelled, abstained, tool error/timeout/denied via `seed.tools[..].status`), es+pt; (b) target scenarios that drive the edited edge (seed values chosen to pick the branch), `expect.outcome` from the finding, `engine.escalated{reason_code}` assertions; sealed before compile. FIFO seeds: scenarios whose branch depends on args are `not_evaluable_native`.
- **Detection evidence.** `collect` with many `max_attempts -> low_confidence` escalations right after one node -> `set_param`/clarify insert; high `fallback_used` or repeated `aclarar` loop -> `swap_template`; "a read tool is called in ~all runs of a segment and its result is re-asked" (SIG-001: leer_movimientos in 77% of dispute cases at the copilot) -> flow REVIEW hypothesis (human), not an automatic edit; a branch `esc_tool` concentration -> tool/service issue, not a flow edit.
- **Minimal first implementation.** Ops `set_param` + `insert_respond_on_edge` on `disputa-cargo` and `consulta-pqr`; goldens: E13 shape plus negative goldens per denial code; live: dry-run valid flow (turns BK0 flow `validate` from `not_exercised` to green) then evaluate with a task or conversational agent per JEV availability.

### 4.2 POLICY (value M for safety/honesty, effort S for hypothesis and M for draft, risk H)
- **P0 (recommended first).** Detection produces a `human_owned_finding` {policy ref, owner, evidence: share of escalations with `policy:<id>` reason code, distribution of the compared value if observable, discrepancy with the policy document (e.g. 250 vs 500, anatomy F6)}. No draft, no Core call. Also expose a boundary-value guard pair in the suite generator (cheap, protects humans' edits too).
- **P1 draft (later, optional).** Representation `{kind:"policy_edit", policy, base_digest, op:"set_constant", path, value}` restricted to a single numeric comparison in a JSON Logic expr. Compiler decides direction from the consuming flow (rule branch `true` -> escalate): only the **tightening** direction (more escalation) compiles; loosening is `policy_loosening_denied`; any policy whose `owner` is not an explicit engine-owned value is `human_owned` -> the draft is labelled `owner_ack_required` and the approver must be the owner. Bump patch; cascade flow+agent+(interrupts using it).
- **Suite.** Base guards fix both sides of the old boundary, so an actual tightening *fails the old yardstick by design* and forces a visible human decision (`scenario_changed` -> accept). That is desirable, not a defect: the engine must say so in the dossier instead of retrying.
- **Evidence.** "Escalation concentration at a threshold" -> P0 hypothesis. Never a Builder-chosen value.

### 4.3 TOOL LINK (value M, effort M after flow, risk M)
- **Exactly which entities change.** For an `agent`-node link: the Flow (node `config.tools_allowed` + prompt rationale if needed), `Agent.tools_allowed`, and the re-emitted unchanged ToolDef copies (+ any template). For a `tool`-node link: the Flow (new `tool` node with `args` from `slots.*/facts.*`, `save_as`, 4 outcome branches), `Agent.tools_allowed`, and the ToolDef copy. Nothing in tool-service changes; there is no grant row to create. Authorization is: ToolDef (`min_auth_level`, `risk_class`) + agent `invocable_by`/`min_auth_level` + principal type accepted by tool-service + FieldClassifier/field grants (deployment).
- **Representation.** `{kind:"tool_link", agent:"consultas@1", tool:"leer_pqr_cliente@1", mode:"tool_node"|"agent_node", at:{flow,edge}, args:{name: slots.x|facts.y}, save_as, on_error:"existing_escalate_node"}`. Tool ref, version and `args_schema` come from the live registry/`/v1/tools`, never from the model. Compiler: read ToolDef, require `risk_class in {read, compute}` (v1), validate args keys against closed `args_schema`, insert the `tool` node pass-through (same insertion machinery as 4.1), wire error/timeout/denied to an *existing* `escalate` node, append to `Agent.tools_allowed`, copy ToolDef, check `source` classified, `invocable_by` ⊆ {customer, advisor}, tool listed by `GET /v1/tools` with same `risk_class`/`min_auth_level`. Denials: `tool_not_in_service`, `write_tool_link_needs_human`, `source_unclassified`, `principal_not_served`, `args_not_in_schema`, `no_error_exit`.
- **Suite.** Scenario per outcome: seed `tool.ok`, `error`, `timeout`, `denied`; `expect.outcome` and `engine.escalated{reason_code:tool_failure}` for the error branches; guards unchanged. Tool identity is not assertable; effect shows downstream.
- **Evidence.** "Agent lacks a tool its peers use" (e.g. consultas has no `leer_pqr_cliente` while the copilot does), repeated `collect` of a datum a read tool already holds, `esc_sin_datos` where the datum is in the customer's data.
