# MAGIC round 1B: agent-core capabilities for the improvement engine (2026-10-04)

Source: agent-core `origin/main` @ 789edc0 (fetched; paths relative to the repo). Read-only. Magic = value a person feels; no robustness work.

## 0. What we use today
`POST /v1/registry/proposals`, `PUT .../draft`, `POST .../validate` (registry/http.py:132-148), `/v1/runs` of `pulso-builder` (api/app.py:218), export pulls `/v1/export/runs|runs/{id}/events|registry-events` (composition/export_http.py:55-80). Not used: freeze, evaluate, approve (human), publish, aliases, lineage, releases diff, outbound events, replay.

## 1. Findings that change the plan
1. **`evaluate` already exists and runs the real engine + real LLM + JEV on the frozen candidate in memory** (registry/service.py:485-550, `SnapshotRegistry`, evaluation/evaluator.py). Unpublished versions never reach prod tables. So "evaluate BEFORE the proposal is tangible" is possible today, but only with **scripted/synthetic scenarios**. The Builder can call `freeze/evaluate` (builder_tools.py:167-181; quota 20 evals/proposal, 10 proposals/day for `auto_detect`, quotas.py:13).
2. **Real-run replay against a candidate does NOT exist.** `Replayer` (audit/replay/runner.py:95) replays a run on the release it recorded (commit f0d4d5f), modes `fixture|audit` only, for determinism audit, not what-if. `dataset` scenarios (real cases) are designed but disabled (`dataset_source_disabled`, registry/suite.py:104-120, TEMAS #20). Audit replay of a real run also reports `diverged` (docs/informes/2026-10-02-flujo-real-y-replay-audit.md section 4).
3. **No canary/traffic split and no multi-alias rollout.** Aliases are only `staging` and `prod` (service.py:139); `promote` moves a pointer, human approver only (service.py:650); a proposal's base is the `staging` alias (service.py:299). `grep canary|traffic` finds nothing. Rollback = promote an older release (humans), `revoke` blocked while prod points at it (service.py:672).
4. **Outbound events exist as a contract, not as a delivery.** `agent_core.outbound` (docs/specs/2026-10-02-eventos-salientes-design.md) defines run.started/closed/transferred, handoff.created/resolved, release.published/promoted/revoked. Relay (relay/service.py) only publishes to an `EventPublisher` port; no webhook/queue is implemented (unit 4). `release.*` lack agent and alias. Engine can already get the same data by **cursor pull** from `/v1/export/*`.
5. **Registry accepts every entity kind except knowledge**: agent, flow, policy, template, prompt, tool, decision_model, language_detection, injection_ruleset, model_profile (domain/entities.py:365-376) plus `RELEASE_SETTINGS` (interrupts, injection ruleset, language detection, max_input_chars; candidate.py:285-320). Knowledge changes rejected `REG-KNOWLEDGE` (candidate.py:112). Locked (platform) interrupts cannot be lowered (REG-LOCKED). New agent = just an Agent draft with its own metrics and suite.

## 4. Gaps to ask agent-core (short list)
(a) `dataset` source enabled for evals, i.e. real-case replay on candidate (TEMAS #20). (b) Canary alias + traffic % + run-creation routing, and rollback signal that is not a human click. (c) Agent id and alias in `release.*` outbound events plus an actual webhook/queue. (d) Knowledge pages in proposals (rejected today). (e) `agentcore replay` by run_id has a `KeyError: 'op'` and audit replay diverges (informe 2026-10-02 section 5): do not rely on it.

## 5. Caveats
Evaluation is synchronous and, in `serve --registry-api`, runs the real LLM and JEV, costing cents per scenario-repetition (default 3 repetitions, up to 200 scenarios): keep suites to a handful for demo. Gate `fail` returns the proposal to `draft` and consumes quota. Approval/publish/promote/revoke are human-only by server-side role check (roles.py), so the engine can never complete the release; the SPA human does.
