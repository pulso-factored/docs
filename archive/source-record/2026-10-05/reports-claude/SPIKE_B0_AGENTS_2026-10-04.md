## 0. Headline facts (the ones that change the plan)

1. VERIFIED. The `agent` node is a free ReAct loop: the model picks tools from `tools_allowed`, and the final answer is validated against an `output_schema` you declare. It calls the llm-gateway (`LLMGateway.generate`, `AC/agent_core/adapters/llm/agent_port.py:49-65`), NOT Jev. So a Core agent can reason with an LLM, and with structured JSON, without `AGENTCORE_JEV_API_KEY`.
2. VERIFIED, and this is the main snag. The model's structured output cannot leave Core over HTTP. Rule G0-22 forbids reading `facts.<agent save_as>` in `end.output_map`, `tool.args`, `rule`, `verify` (`AC/docs/specs/motor/m01-validacion-estatica.md:437`); the only exception is `value.changes` of a DRAFT_OUTPUT_SCHEMA agent into a `write_draft` tool (`:453`). `POST /v1/runs` returns `output` only from `end.output_map` (`AC/agent_core/interpreter/handlers/terminal.py:27-33`; `AC/agent_core/turn/engine.py:880-890`). `agent_step` events carry only a keyed fingerprint (`text_fp`, `AC/agent_core/domain/events.py:164-178`). Our own `core-bridge` reads run facts in-process (`OURS/core-bridge/src/pulso_core_runtime/invoke/projection.py`), which is impossible against the shared Core. Workaround (inferred, not tried): give the agent a read/compute tool whose args are the structured result, implemented in OUR tool service (`pulso/submit_hypotheses`). Tool args are model-written JSON (ADR 0025 contract) and the engine does not validate them against `args_schema` itself (`AC/agent_core/interpreter/handlers/tool.py:33-45` and `HttpToolExecutor.execute` just forward), so our service must validate.
3. VERIFIED. There is exactly ONE tool service per Core process (`AGENTCORE_TOOL_SERVICE_URL` + `_TOKEN`, `AC/agent_core/adapters/tools/http_executor.py:32-35,150-170`). Only `registry/*` is routed elsewhere (`RoutedTools`, prefix `registry/`, `AC/agent_core/composition/builder_tools.py:208-228`, wired at `AC/agent_core/composition/serve.py:153-155`). The platform's own tool service is "Proposed, no code yet" (`SP/docs/platform/adr/0004-tool-service.md:3`). So `pulso/*` tools can only exist if our service IS that service, or sits behind a router the Core operator controls (`serve --tools module:attr` is the plug-in point, present at `c814c2b` too: `AC/agent_core/composition/serve_ports.py:57`).
4. VERIFIED. Tool results shown to the model go through M7: any field not in the deployment's `FieldClassifier` is `pii_direct` and is TOKENISED (`AC/agent_core/views/classification.py:46-47,76-91`, `AC/agent_core/views/service.py:185-190`). A `ToolDef.source` for our tools needs a `public` entry in the Core's classifier (a deployment factory, `--field-classifier`), or the model reasons over `⟦pii:1⟧` instead of numbers. Our bridge solved this with `LAB_CATALOG` (`OURS/core-bridge/src/pulso_core_runtime/factories.py`).
5. VERIFIED. A NEW agent enters the registry in one of two ways, both needing a human admin: (a) `agentcore registry import <dir>` (CLI with DB DSN, `require_admin` = human + `step_up`, creates the release and points `staging` AND `prod` at once, `AC/agent_core/registry/service.py:801-846`; there is no HTTP route for it, `AC/agent_core/registry/http.py:132-220`); (b) the proposal API with `agent_id` of the new agent and base release `None` (supported: `AC/agent_core/registry/candidate.py:268-300`, "first publication has no alias to lock", `service.py:600`), which needs an `eval_suite` in the draft, `evaluate` pass, a human approver at `step_up` (`roles.py:50-63`), `publish` (-> `staging`) and `promote` (-> `prod`). The e2e fixture registry has NO eval suites (`AC/docs/runbook-e2e.md:section 5, point 3`), so route (b) has never been exercised on their side.
6. VERIFIED. We already built these agents once, for our own Core: `OURS/agent-core-assets/worlds/pulso-evolution` (`pulso-scout`, `pulso-verifier`, `pulso-builder-design`, `pulso-writer`; task mode, `invocable_by: [builder]`), `pulso/*` ToolDefs, model profile, and `OURS/core-bridge` composes `agentcore serve` with our own 7 factories and a `pulso/*` dispatcher. That is the "Core externo" the user dropped; it is the cheapest reference implementation and the cheapest demo, but it is not the shared Core.

## 2. Agent definition format and authoring path

**Entities** (VERIFIED, `AC/agent_core/domain/entities.py`, `.../domain/nodes.py`): YAML files per kind in a registry directory: `agents/`, `flows/`, `prompts/`, `templates/`, `tools/`, `decision_models/`, `model_profiles/`, `policies/`, `language_detection/`, `injection_rulesets/`, `releases/`, optional `eval_suites/`, `calibrations/` (layout = `registry-e2e` fixture, `yaml_io.py:20`). Schemas are generated JSON Schema in `AC/contracts/schemas/*.json` (do not hand-edit; `agentcore contracts`). `ID_PATTERN = [a-z0-9][a-z0-9_/-]*` so ids like `pulso/get_signal` and `pulso-scout` are legal (`AC/agent_core/domain/base.py:46`).

**Agent fields** (`entities.py:63-90`): `id, version, mode (conversational|task), entry_flow, invocable_by[principal types], min_auth_level, subject_kinds, supported_locales, default_locale, tools_allowed, budgets, inactivity_ttl, understand?, slots_model?, templates{7}, max_clarifications, on_clarify_exhausted, default_target_queue, metrics?, routing?, accepts?, input_schema?` (`input_schema` only for task agents, `:92-93`).

**Closed node catalogue** (`nodes.py:366-383`, outcome keys `:385-400`): `decide`, `rule`, `collect`, `tool` (read) / `tool` with `draft:true` or `action_from` (write), `confirm`, `verify`, `respond` (template or generate), `escalate`, `end`, `knowledge`, `agent`, `subflow` (rejected by G0-01), `await_approval`, `transfer`. Task flows may not contain `collect`, `confirm` or `respond(await)` (G0-16, `m01...:196`). An `agent` node needs a prompt whose profile is `structured: prompted` (G0-25, `:454`) and every tool in `tools_allowed` of that node must be `read`/`compute` with `description` and `args_schema` in the closed JSON-Schema subset (G0-07, G0-24, `:187,:202`; runtime check `handlers/agent.py:116-121`).

**Authoring path for a NEW agent (no platform builder involvement possible):**
- By repo fixtures + operator: write the YAML directory, `agentcore registry import <dir>` (admin human + step_up + DB DSN). Fast (minutes), immediate `prod`. Only possible once per agent id ("already has releases; use a proposal", `service.py:821-823`).
- By proposal API: `POST /v1/registry/proposals {agent_id, origin, title}` (`registry/http.py:132`), `PUT .../draft`, `.../validate`, `.../freeze`, `.../evaluate {suite_id}`, `.../approve`, `.../publish`, `POST /aliases/{agent}/{alias}` (promote). Only the first four are possible for our non-human `builder`/`constructor` identity. `approve/publish/promote/revoke` need a human with role `aprobador` and `auth.level=step_up` (`roles.py:50-63`), minted in the platform per call with a TOTP code and valid 2 minutes (`SP/.../adr/0003...:39`). The platform builder screens (S16) are a registry client and would work for this, but the platform builder lists only its own index (`builder_proposals`) until our proposal is tracked by id (`SP/.../adr/0003...:40`, `builder_chat.py:279-297`).
- Namespacing/versioning: semver exact per entity; releases are immutable and pinned; `staging` set by publish, `prod` only by promote (ADR 0018 point 7, `AC/docs/adr/0018-propuestas-y-gate-de-publicacion.md:26`). Release ids are content hashes (`release_id_for`). No tenant concept anywhere (grep `tenant` over AC and SP backend: no hits). Names are global in one registry: use a prefix (`pulso-scout`, tools `pulso/...`), and the `registry/` and `directory/` prefixes are reserved by the engine.
- Who approves: a human with the aprobador role. Time: UNKNOWN (org dependent); technically minutes by import, or a proposal cycle plus an eval suite for the other route. Nothing says an infra agent has a special approval track (UNKNOWN).

## 3. Invoking a Core agent from an external service with structured input/output

**Invocation (VERIFIED):** `POST /v1/runs {agent: "pulso-scout@prod", subject?, input?{...}, lang?}` + `Idempotency-Key` (required; replay returns the stored result, same key with a different body is 409; `AC/agent_core/api/app.py:212-235`, `turn/engine.py:780-800`). A task run executes the whole flow synchronously inside that request and returns `RunResult{run_id, release, output?, status, outcome, trace_id}` (`domain/turn.py:84-94`, `turn/engine.py:880-890`). No `session_id` for task runs. `GET /v1/runs/{id}` returns only a summary.

**Input shape (VERIFIED):** `input` is a flat map. With `Agent.input_schema` the engine validates and the slots enter as `validated`; the slot types are only `string|integer|decimal|date|boolean`, no objects or arrays (`AC/agent_core/domain/transfer.py:14,25-29`; `turn/engine.py:810-820`). Without `input_schema` the slots are `claimed` and a flow reading them fails AG-04 (`flows/agent.py:49-66`). So "free-form structured input" must be (a) IDs/refs as strings that the agent resolves by calling our tools, or (b) a JSON string slot. Slots are shown to the model wrapped as untrusted text (`interpreter/projection.py:55-57`). Pattern: a `tool` node first (`pulso/bind_job`, args from a validated slot) so OUR service learns `run_id -> job` from `context.run_id` before the model starts calling tools with model-written args.

**Output (VERIFIED):** see headline 2. Options ranked: (1) `submit_*` callback tool (our service receives validated JSON; the agent's own final output is a tiny ack); idempotent tool required because idempotent tool nodes are retried twice (`handlers/tool.py:26,61`) (agent-node calls are not retried); (2) for the Builder only, the draft path (`output_schema = DRAFT_OUTPUT_SCHEMA` -> `registry/put_draft`), which writes Core entity content itself, bypassing our compile step. Reading `RunResult.output` works only for values the FLOW computes from tools/slots, never from the model.

**Auth (VERIFIED):** JWS Ed25519 compact, header exactly `{alg: EdDSA, kid, typ: principal+jws|delegation+jws}`, payload = serialised `Principal{type, id, roles, scopes, attrs, auth{level, at, simulated}, exp}`; NO audience, NO issuer, NO tenant claim; validity is `exp` checked with Core's clock (`AC/agent_core/adapters/jws_identity.py:3-8,25,78-92`; issuer example `SP/.../infrastructure/ai/ed25519_issuer.py:1-143`). Verification keys come from a YAML/JSON file `{principal_keys:{kid:b64url}, delegation_keys:{...}}` (`--identity-keys`) and a separate `--staff-keys` file for the registry; both files are re-read every 5 s (`serve_ports.py:277`, `identity_keys.py` docstring), so adding our engine's public key needs an operator file edit but no restart. Principal types: `customer|advisor|service|builder` (`domain/identity.py:11-16`). The runtime (`/v1/runs`) verifies against identity keys; the registry against staff keys; a staff-signed credential on a run is `credentials_invalid` (`SP/.../adr/0003...:38`). Registry operations demand a `builder` (never a `service`: `roles.py:30-34`), run creation accepts `service` (rate limit x10 vs others, `api/limits.py:33-46`). `AuthzPort.authorize_agent` decides `invocable_by`/`min_auth_level`/`subject_kinds`; the only implementation in the repos is the permissive demo double (`AC/testing/fakes/authz.py:50-62` shows the intended rule); the platform has no real one yet (`SP/.../adr/0003...:62`, runbook "invocable_by not enforced in demo"). Our bridge's `PulsoAuthz` (`OURS/core-bridge/.../factories.py`) accepts `builder` with a stage role. The engine's identity is therefore: `invocable_by` must list the type we sign (`service` for Scout/Verifier is natural; `builder` is what our bridge uses and is required for any `write_draft` flow, AG-02, `flows/agent.py:79-90`).

**Limits (VERIFIED):** per agent in `Agent.budgets` (we choose the numbers: constructor-chat uses 8 model calls/turn, 60k tokens/run, 1.00 USD/run, 60 s wall; our own assets use 16 calls, 120k tokens, 5.00 USD, 900 s). Run budget is checked before every step; exhaustion escalates `budget_exceeded` (`interpreter/budgets.py:43-54`, `handlers/agent.py:166-167`). Per principal: 30 turns/60 s and 5.00 USD/day by default, x10 for `service` (`api/limits.py:33-41`, env `AGENTCORE_RATE_*`, `AGENTCORE_DAILY_BUDGET_USD`, `serve.py:47-62`). Tool call timeout 10 s by default for ALL tools (`AGENTCORE_TOOL_SERVICE_TIMEOUT_S`, `http_executor.py:35,165`), so a slow callback (SQL over a lab) needs a deployment-wide raise. LLM call timeout = `ModelProfile.timeout_s` (gateway accepts up to 300 s, `GW/api/openapi.yaml:235`); gateway body limit 1 MiB (`GW/internal/config/config.go:95`). Concurrency: UNKNOWN as a number; a run holds one worker thread for its whole duration (sync handler) and Core is stateless/horizontally scalable (ADR 0023).

## 5. LLM plumbing, minimum to make an agent reason at main

- VERIFIED: `AGENTCORE_JEV_API_KEY` is NOT required to start or to run an agent that has no `understand`/`decide`/`providers: jev`. Core builds `JevProvider(HttpJevTransport(lambda: _jev_key(env), clock))` lazily and only a call raises "falta AGENTCORE_JEV_API_KEY" (`AC/agent_core/composition/serve_ports.py:174-178,349`). `Agent.understand` is optional (`entities.py:73`); conversational agents need it, task agents do not. constructor-chat does need Jev (its `understand-constructor`).
- VERIFIED required: `AGENTCORE_LLM_GATEWAY_URL` + `AGENTCORE_LLM_GATEWAY_TOKEN` together (`serve_ports.py:198-217`); without them `UnconfiguredLLMGateway` and every generation fails (`:347-348`; agent node then ends `gave_up`, `handlers/agent.py:173-178`). Gateway side: `LLM_ENDPOINTS` JSON `{alias:{base_url, api_key_env}}`, `GATEWAY_CONSUMERS` `{name:{token_env}}` (`GW/internal/config/config.go:19-51,119-150`); the provider key (OpenRouter) lives only in the gateway env, referenced by alias from the Core's `ModelProfile.endpoint_alias`.
- VERIFIED gateway surface: `POST /v1/generate` (OpenAI-compatible chat via alias, one call, no retries, cost computed from the price in the profile you send, `GW/docs/consuming.md:11-60`), `POST /v1/jev` (Jev pass-through holding the key, `GW` PR #2). Core at `547e608` does NOT use `/v1/jev`: its Jev transport posts straight to the Jev base URL with its own key (PR #28 "JEV via gateway" is stranded, per `PLATFORM_ATTACH_PLAN` fact 2; I did not re-verify the PR branches).
- Free text/JSON without Jev: VERIFIED yes, three nodes: `agent` (ReAct, structured output), `respond.generate` (text only, validated by M8 numbers/PII validators, template fallback mandatory: G0-09), and Jev-free `decide` only with `llm_structured`/`classifier`/`rule` providers (`ProviderSpec.provider` enum, `entities.py:326-329`; calibration/thresholds required for decide branches, so not a free generator).
- Mode of the agent step: `structured: prompted` only; `native` profiles are rejected (`agent_port.py:67-75`). Output must fit the Core JSON-Schema subset (`type, enum, properties, required, additionalProperties(bool), items`: our own `OURS/core-bridge/.../stages/catalog.py` header documents the same limits; no minItems/pattern).
- Budget/cost knobs: `Agent.budgets` (per run), `ModelProfile.{model, temperature, max_tokens, timeout_s, price}`, gateway-computed `cost_usd`, per-principal daily USD and hit limits, tool timeout env.

## 7. How to trigger the engine

- agent-core, pull only, VERIFIED: `GET /v1/export/runs?after=<cursor>&limit<=500` (cursor = commit order of the run's last change; a run reappears when it changes, so `run.closed` = a changed row with status closed), `GET /v1/export/runs/{id}/events?after=<seq>` (seq contiguous per run, hash chain detects gaps), `GET /v1/export/registry-events?after=<n>` (published/promoted/revoked/imported/proposal_* in registration order). Requires a builder principal with role `exporter` (or admin), staff-key signed, no human/step-up (`AC/agent_core/composition/export_http.py:40-80`, `registry/roles.py:43-47`, `ports/export.py` docstring). Our `core-bridge` already contains an `exporter/` package built around these cursors.
- agent-core push: SNS relay only (opt-in `AGENTCORE_EVENTS_TOPIC_ARN`, `agentcore relay`), `release.*`/`handoff.created` in v1; no webhook, no SSE.
- Platform: VERIFIED no webhook, no SSE for services, no export endpoint. `event_log` is append-only, written in the same transaction as the state change, then published to an in-process bus (`SP/docs/platform/adr/0001-architecture.md:58-71`); `sequence` is an integer autoincrement PK used for cursor pagination (`.../tables.py:504-507`); the only readers are the audit routes (`api/routers/audit.py`). The `EventExporter` was REMOVED on 2026-10-03 (`adr/0001:108-113`). Sequence contiguity: the docs promise "monotonically increasing" and "total arrival order", and gapless only for `turns.sequence` per case (`DATA_MODEL.md:110,412,568`). Gaplessness across rollbacks and out-of-order visibility under concurrent commits are database behaviour: UNKNOWN for their eventual Postgres (S17) and unverified for SQLite. Treat the cursor as "monotone, maybe sparse, maybe late": poll with a watermark overlap and dedupe on `event_id` (our `sources` crate watermark store already does overlap-style polling per the plan).
- Platform event types usable as triggers (`DATA_MODEL.md:575-590`): `case.opened/closed/rated`, `escalation.*`, `turn.created`, `copilot.query_asked/answered` (sizes only). Our read-only adapter polls the DB, which needs nothing from them.
- Dedup/idempotency for us: derive `trigger_key`, and use it as the `Idempotency-Key` of `POST /v1/runs` so a re-run does not spend twice (409 on body change).

### 8.2 What each blocker costs and who holds it
1. Tool routing (single URL): cheapest = Core operator points `AGENTCORE_TOOL_SERVICE_URL` at our service for the demo environment and our service proxies unknown tools (or the platform's future tool service forwards `pulso/*`). At the pin `c814c2b` there is no HttpToolExecutor at all, so the pin must move to `547e608` or the operator must run a custom `--tools` factory (we have one).
2. FieldClassifier: one `public` entry per `ToolDef.source` (e.g. `pulso_signal`, `pulso_extract`) in the Core's classifier factory (today a demo double; platform plans to load the data-pipeline catalog and `unclassified -> pii_direct`).
3. Registering the agents: admin human runs `agentcore registry import <our seed dir>` (reuse `OURS/agent-core-assets/worlds/pulso-evolution` after dropping `jev-evolution-route` and the writer, and sharing `t/*`, `injection-rules`, `lang` entities that import requires to be present in the same root). Alternative, slower: proposal path with an eval suite and a human step-up.
4. Identity: our public key into `--identity-keys` (hot reload 5 s) and `--staff-keys` for the writer; agent types must be allowed by their `AuthzPort` (today permissive demo).
5. Gateway: a consumer token for the Core, an OpenRouter alias and key in the gateway env (both owned by the Core operator).
6. Not blockers: JEV (not needed), tenant (does not exist), streaming (not needed), concurrency (not a documented limit).

### 8.3 Go / no-go
- Path C (agents in the shared Core): GO as the target and as an additive backend (`CoreAgent`) behind the same `ModelPort`, NOT as the critical path of a one-day demo. It is technically sound (agent node + gateway + our tool callbacks) but every enabling step in 8.2 is outside our repos and needs a human admin; none of it has been exercised on the shared Core, and no task-mode agent with an `agent` node exists in AC fixtures (tests exist: `tests/m02/test_agent.py`, `tests/m04/test_start_run.py`, `tests/u05/*`; a live one is unproven).
- Path G (engine calls the gateway directly): GO for the demo. The Gateway backend already exists (~70% built per the plan) and only needs a gateway consumer token + provider key. Keep the exact role contracts (schemas, prompts) so that the three prompts and output schemas migrate 1:1 into `p/*` + `output_schema`/`submit_*` args for Path C.
- Shortest path to a demo in about a day: (1) Path G with a real model on synthetic data (our `roleplay-llm` + `Gateway` backend), (2) in parallel, send the Section 9 asks, (3) if the user wants to SHOW Path C that same day, the only no-dependency way is our own local stack (`OURS/core-bridge`, `OURS/local/core`, worlds `pulso-evolution`), which already runs the three stages as Core agents against our pinned Core; label it honestly as a Pulso-owned Core, not the shared one.
