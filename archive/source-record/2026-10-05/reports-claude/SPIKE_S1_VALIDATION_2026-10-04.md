## H1: tools, principals, limits (file:line)

- Tools: `BUILDER_TOOL_DEFS` has 10 `registry/*` tools: write_draft `create_proposal`, `put_draft`, `freeze`, `reopen`, `evaluate`; compute `validate`; read `get_proposal`, `get_entity`, `list_versions`, `get_write` (`AC/agent_core/composition/builder_tools.py:51-72`). No approve/publish/promote/revoke tool exists (docstring `:5-6`).
- Routing: `RoutedTools` sends the prefix `registry/` to `BuilderToolExecutor` and everything else to the deployment executor (`:208-228`), wired only when `ports.registry_api is not None` (`AC/agent_core/composition/serve.py:153-155`). The executor never checks WHICH agent calls: any agent listing the tools in `tools_allowed` gets them (grep over `agent_core` finds no allow-list).
- Principal: the bot is `builder`, role `constructor` only, no `actor=human` (`serve.py:86-90`); registry service requires `require_constructor` (`AC/agent_core/registry/roles.py:30-40`). The run principal is only audit (`builder_tools.py:142-148`). Approve/publish/promote/revoke need a human with step_up (`roles.py:50-63`).
- Agent constraints (experiment exp2, X7/X8): a flow with a `write_draft` node and `invocable_by` containing `service` gives violation AG-02 (`AC/agent_core/flows/agent.py:81-89`); `subject_kinds` must be empty. So our engine must sign a `builder` principal for `pulso-builder` runs (`AuthzPort`: `PolicyAuthz.authorize_agent` checks `principal.type in agent.invocable_by`, PR 34 `policy_authz.py`). Rate-limit multiplier x10 applies only to `service` (`AC/agent_core/api/limits.py:31-32`), so a builder run gets 30 hits/60 s and 5 USD/day.
- Inside the `agent` node only read/compute tools (G0-07, X9 fails; `handlers/agent.py:116-121`). So `freeze` and `evaluate` must be `tool` draft nodes with their own `verify` (G0-23); X6 shows a create/put/validate/freeze flow validates. `evaluate` as a node is synchronous real LLM work inside the run; safer to call evaluate over the registry HTTP API from our service (same bot rules and quotas).
- Quotas (`AC/agent_core/registry/quotas.py:11-14`, `service.py:288-295,497-500`): only for `origin=auto_detect`: 10 proposals per rolling 24 h, counted GLOBALLY (not per actor), 20 evaluations per proposal. Over quota is `denied`. `origin` enum allowed to the bot: `builder_chat`, `auto_detect` (`builder_tools.py:41`).
- `expected_rev`: `put_draft` raises `proposal_stale` if the proposal rev differs (`service.py:339-341`); the flow passes `facts.propuesta.value.rev` straight from `create_proposal`, so a single run is safe. Idempotency: tool writes carry the engine action id as idempotency key (`service.py:270-272`); a new run creates a new proposal, so dedupe must be the run's `Idempotency-Key` (replay returns the stored result, `turn/engine.py:780-800`).
- put_draft limits: max 50 changes, 262144 bytes per entity (`registry/validation.py:15-19`); platform guardrail edits rejected `forbidden_role` and interrupt changes need admin (`service.py:316-345`).
- The Builder agent itself is a new agent: enters by `agentcore registry import` (admin human) or a proposal with eval_suite plus human approve/publish/promote (SPIKE_B0 section 2). Unchanged.

## H2: input and output (experiments)

- exp2 X1/X2: a task agent (`mode: task`, `input_schema` of three string slots, `invocable_by: [builder]`) whose flow is agent node (output_schema = `DRAFT_OUTPUT_SCHEMA`) -> `create_proposal` -> verify -> `put_draft` (changes from `facts.borrador.value.changes`) -> verify -> `validate` -> `end completed` with `output_map {proposal_id: facts.propuesta.value.proposal_id, valid: facts.validacion.value.valid, rev: facts.propuesta.value.rev}` validates with zero problems. End outcome must be `completed` (outcome `resolved` makes the flow conversational: AG-01).
- Negatives (all rejected by G0-22): `output_map` reading `facts.borrador...` (agent fact) X3; reading `facts.guardado...` (put_draft result, tainted) X4; agent output with a schema other than the draft one feeding put_draft X5. Rule text: `AC/docs/specs/motor/m01-validacion-estatica.md:437,453`; implementation `AC/agent_core/flows/rules/phase5.py:350-385` (taint set = agent save_as plus draft writes that read it; `create_proposal`'s save_as is not tainted).
- exp5: real interpreter, real `BuilderToolExecutor` over the in-memory registry, scripted agent step: run ends `terminal/completed`, output `{'proposal_id': 'proposal-0001', 'valid': True}`, proposal `draft`, `origin=auto_detect`, `created_by=constructor-bot`, one change. (Run principal in exp5 was `service`; the AG-02 check is static, runtime does not recheck.)
- Limits of string slots: types only `string|integer|decimal|date|boolean` (`AC/agent_core/domain/transfer.py:14,25-29`); no per-slot max length; `max_input_chars` (4000) guards user TEXT turns only (`guards/service.py:56`), start_run applies only `packet_problem` (`turn/engine.py:810-820`). HTTP body size: not found in `api/`; the practical cap is the gateway body limit 1 MiB per model call (`GW internal/config/config.go`, `MAX_BODY_BYTES`).
- PII tokenisation of inputs (exp3): the agent sees `slots.*` wrapped as `<datos_no_confiables fuente="slots">...` and passed through the PII detector: digit runs of 6 or more digits with separators, emails, long numbers become tokens (`⟦doc:n⟧`, `⟦prod:n⟧`). Example: `ci=[0.88,0.97]` -> token, `window=2026-09-01..2026-09-30` -> token, `amount_total=1342800` -> token. `detokenize` runs ONLY on the model's tool-call args (`handlers/agent.py:50-58,122`), not on its final output, so a token the model copies into `changes` lands in the draft as literal `⟦doc:1⟧`. Mitigation: write evidence with short numbers, no ranges with dots/commas, ISO dates alone, ids as words; or give ids and fetch evidence via a tool (needs tool routing, H4).

- Budgets: `Agent.budgets` (we choose; constructor-chat uses 8 model calls, 60k tokens, 1.00 USD, 60 s). Each ReAct step resends inputs+observations+tool catalog+output_schema as one JSON user message.
- Not proven live: no task agent with an `agent` node exists in the fixtures; the interactive copilot (`asistir@1`) exercises the agent node live per PR 34's runbook.

## H4: tool-service, routing, classification

tool-service (`pulso-factored/tool-service`, 3 authors from the agent-core/platform team: Juan Jose Zapata; Python/FastAPI+DuckDB):
- What it is: HTTP tool provider over `gold_restricted` customer data: 7 tools (`leer_productos`, `leer_perfil`, `leer_movimientos`, `buscar_transacciones`, `leer_pqr_cliente`, `radicar_pqr`, `obtener_pqr`), `POST /v1/tools/{id}/execute`, `GET /v1/tools`, bearer consumer tokens `TOOL_SERVICE_TOKENS` (`TS/src/tool_service/app.py:76-125`, `settings.py`).
- Declaration: a `ToolSpec` in `CATALOG` (`TS/src/tool_service/tools/__init__.py:7`) plus a registry yaml generated by `scripts/export_registry.py`; the registry owns the ToolDef, the service implements by id. Ids are bare names (`leer_perfil`).
- Claims model (ADR 0025, PR 11 ADR 0004): agent-core sends verified CLAIMS (principal type/id/roles/scopes/attrs/auth_level, subject, on_behalf_of), never a JWS, trusts the bearer (`AC/agent_core/adapters/tools/http_executor.py:116-132`). PR 11 only rewrites ADR 0004 to say this; no new blocker.
- Blocker for our tools: `Service.execute` resolves a customer subject for EVERY tool and answers `denied principal_not_served` for any principal other than customer/advisor (`TS/src/tool_service/subject.py:29-49`, `app.py:50-52`). A `builder`/`service` principal calling a `pulso_*` tool would be refused. Adding our tools means a PR in their repo (a ToolSpec flag `subject_required: false` plus allowed principal types) and putting engine-signal logic in a customer-PII service; poor fit. A second URL is impossible today: `HttpToolExecutor` has one URL, one token, one timeout (`http_executor.py:146-160`), `RoutedTools` only special-cases `registry/`.
- Tool id with slash: executor URL-quotes the id (`http_executor.py:66`); FastAPI `{tool_id}` does not match a decoded slash, so ids like `pulso/get_signal` would 404 on tool-service. Use slash-free ids (`ID_PATTERN` allows `_` and `-`: `AC/agent_core/domain/base.py:46`), e.g. `pulso_get_signal`.
- PR 34 (`721befa`, `275c006`): `AGENTCORE_FIELD_CLASSIFICATION_FILES` = comma-separated JSON files, merged in order, later wins; unclassified stays `pii_direct` (`adapters/classification.py`, factory `agent_core.adapters.classification:field_classifier`); `scripts/e2e/serve-tools.ps1` serves with http tools + PolicyAuthz + published catalog + `scripts/e2e/field-overlay.json`.
- Overlay content (24 keys, all bare names): `directory.choices`, `directory.entries.{agent_id,release_id}` public, `directory.entries.{summary,examples}` untrusted; `valor` financial; `moneda`, `fecha`, `fuente`, `speaker`, `case_id`, `topic`, `target_queue`, `id`, `status`, `transaction_id`, `filed_at` public; `resumen`, `concepto`, `detalle`, `reason`, `summary`, `text`, `description` untrusted. "The engine's own fields" means the Core's own fields (directory, copilot/agent-written values), NOT ours. None of `cell`, `rate`, `n`, signal fields are present.
- Our evidence fields: exp3 shows with the default classifier every field of a tool result (cell, rate, n) becomes `⟦pii:n⟧`; exp4 shows a single catalog entry `{"pulso_signal": {"field_class": "public"}}` (container-level, keyed by `ToolDef.source`) makes nested numbers and strings pass in clear (children inherit; explicit strict PII names such as `email` in the published catalog still win). So: no code change, one extra JSON file appended to `AGENTCORE_FIELD_CLASSIFICATION_FILES` by the Core operator, and PR 34 merged (on main, serve uses the demo classifier double `testing.serve_demo`). Classification key is the ToolDef `source` in the registry, not the `source` in the tool response (`handlers/agent.py:126-128`, `interpreter/projection.py:76-84`).
- Also needed for the Builder agent: results of `registry/get_entity` etc. are projected under source `registry/get_entity` with the default rule (exp3: fields become `⟦pii:n⟧`); the constructor-chat agent shares this, so add `registry/get_entity`, `registry/list_versions`, `registry/get_proposal` containers as public to the overlay if the Builder must read artifact text through tools.

## H5: gateway and model

- Core step format: prompted JSON, `STEP_SCHEMA {kind: tool_call|final, tool, args, output}` (`AC/agent_core/adapters/llm/agent_port.py:28-38,62`); `native` profiles are rejected (`:67-75`). So no native tool-calling or `tools` parameter is needed: any chat model that follows "answer only a JSON object" works.
- Gateway `/v1/generate`: plain `POST {base_url}/chat/completions` with system (prompt + fixed schema instruction) and user (canonical JSON of inputs), `temperature`, `max_tokens`; `response_format` only in `native` mode; no tools, no `reasoning`, no provider-routing fields (`GW internal/gateway/call.go:87-111`). Output parser strips code fences and checks the schema subset (`internal/schema/schema.go:159-172`). `finish_reason: length` => `invalid_output` "truncated output" (`call.go:154-157`); `content` null with reasoning-only output => unparseable.
- Config: endpoints `LLM_ENDPOINTS={alias:{base_url,api_key_env}}`, consumers `GATEWAY_CONSUMERS` (`GW internal/config/config.go:19-51`); model/temperature/max_tokens (1..1,000,000)/timeout_s (1..300)/price travel per request from the Core's `ModelProfile` (`AC http_gateway.py:99-105`). No model allow-list anywhere; a wrong id reaches OpenRouter and returns non-2xx => `unavailable` (502) (`call.go:68-69`).
- Fixture profile has `max_tokens: 400` (`registry-e2e/model_profiles/perfil-generacion@1.0.0.yaml`): ship our own profile (suggest 4000 to 8000, `timeout_s` 60 to 120, `structured: prompted`, real price).
- `deepseek/deepseek-v4.1-flash`: UNKNOWN. The id is not listed in any clone (grep over agent-core, platform, gateway, tool-service found none). Settling: one OpenRouter `GET /api/v1/models` read (no model call) to confirm the id, tool/structured support flags, and whether it is a reasoning model that needs a large `max_tokens`. Independent Verifier on the same model: unchanged risk.

## Alignment with ADR 0018/0019

ADR 0019 decisions 2-5 and the 2026-09-30 amendment describe exactly our Builder: a `task` constructor activated by a signal, principal `builder`, registry decides with its own credential (`constructor-bot`), `write_draft` without confirm, `DRAFT_OUTPUT_SCHEMA` exception to G0-22, origin `auto_detect`. ADR 0018: constructor/detector advance at most to `evaluated`, never approve/publish/promote/revoke; humans approve (decision 6); gate failure returns to `draft` (5); proposal budgets (10); the auto-detect cap values (10/day, 20 evals) are the "topes del constructor autónomo" left open in 0019 and implemented in `quotas.py`. The task constructor agent itself is listed as "Pendiente" (not in fixtures), and the ADR notes AG-01 prevents sharing flows with the conversational one (separate flow, shared tools/prompts). Terminology to reuse: constructor-bot, `write_draft`, `DRAFT_OUTPUT_SCHEMA`, `auto_detect`, candidata/freeze, gate, aprobador.
