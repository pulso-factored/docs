## Codex hypotheses

1. consultas needs a bound knowledge source: HOLDS. The registered flow `consulta-pqr` only collects a `radicado` and calls `obtener_pqr` (the agent's only tool); there is no knowledge node or port. Factual cases (payment date, available limit, hours) end `abstained` (or escalated), never `resolved`. Native evaluate has no knowledge binding, so these cannot be asserted resolved; a `resolved` case needs a radicado in the text plus a seeded `obtener_pqr`.
2. recepcion `transferred` needs a bound transfer target/action: HOLDS, stronger form. The flow needs `directory/list` (engine-served from an `AgentDirectory`) to produce choices, then a `transfer` node. Evaluate builds the engine without a directory. A probe that seeded `directory/list` (entries + choices) still ended with no outcome, not `transferred`: so `transferred` is not reachable through native evaluate; keep it distinct from `escalated` and do not assert it there.
3. dispute generic/refund/threshold vs policy `escalamiento-disputa-monto` (> 500 USD): PARTLY. The implemented threshold is 500: seeded probes at 200 and 300 USD resolved with no escalation; 600 USD escalated. So a 250-based assertion would mismatch the registered policy, but the generic/refund/below-limit scenarios fail because they are UNSEEDED (tool failure escalates), not because of the policy: the same 200 USD case with the tool seeds resolves. Seed `convertir_moneda` with a number, not a string.
Also: all three registered agents use `on_clarify_exhausted: escalate`, so `clarify_exhausted` expectations are unsupported by these assets (README assumes `end`).
